# 第一章 绪论

## 1.1 研究背景与意义

### 1.1.1 行业背景

随着新能源汽车保有量持续攀升，充电基础设施已成为城市交通与能源体系的关键组成部分。
充电桩的"总量不足"问题正在逐步缓解，但**结构性失衡**问题日益凸显：
一方面是部分区域充电资源闲置，另一方面是核心功能区在高峰时段排队等候严重。
运营商在布点决策时往往依赖经验判断或简单的人口密度指标，
缺乏对"哪个分区、哪个时段、缺多少容量"的量化认知。

在此背景下，对充电设施运行数据进行系统分析，
从中挖掘分区级的供需结构特征并形成可执行的优化建议，
具有明确的现实意义与应用价值。

### 1.1.2 技术背景

随着单站数据规模持续增长，单机处理方式在以下方面逐渐显现不足：

- **存储层面**：多源、多粒度的运行数据持续累积，传统单机文件系统在容量与可靠性上受限
- **计算层面**：宽表转长、空间连接、多维聚合等操作单次计算量大，串行处理耗时长
- **分析层面**：分析口径需在不同角色（运营方、车主、城市管理者）之间统一，需要分层的数据组织

Hadoop 生态为这类"**海量数据存储 + 批处理计算 + 分层数据组织**"的典型场景
提供了成熟解决方案：HDFS 提供高可靠的分布式存储，
MapReduce 与 Spark 提供分布式计算能力，
Hive 提供数据仓库与分层建模支持，
Sqoop 完成关系型数据库与数据仓库之间的数据交换。

本课题正是将这一技术栈应用于充电桩运行数据的分析场景中。

### 1.1.3 研究意义

**理论意义**：本课题将时序数据仓库方法论应用于城市充电基础设施领域，
验证了"ODS-DWD-DWS-ADS 四层建模"在时空细粒度能源设施数据上的适用性，
为同类垂直领域的离线分析系统提供了可复用的架构范式。

**实践意义**：系统输出的分区级供需失衡指数、分时电价引导效果评估
与布点扩容建议，可直接服务于运营方的日常调度与规划决策，
将"经验判断"转化为"数据支撑"。

## 1.2 国内外研究现状

### 1.2.1 电动汽车与充电设施研究

国际上对电动汽车充电行为的研究起步较早，主要方向包括：充电需求预测（基于马尔可夫链、
混合效应模型、深度学习等）、充电站选址优化（选址-分配模型）、
以及车网互动（V2G）调度策略等。
这些研究普遍使用北美、欧洲的公开数据集，模型方法相对成熟。

国内相关研究近年来快速增加，数据来源多为自采问卷、
运营商合作数据或仿真生成数据。
由于充电设施数据涉及运营敏感信息，**公开可复现的高质量数据集相对稀缺**，
这在一定程度上制约了研究的可重复性。

### 1.2.2 时序数据仓库与 ETL 研究

Hadoop 与 Hive 的分层数仓模型（ODS-DWD-DWS-ADS）
自提出以来已成为业界标准实践，相关研究已相当充分。
然而在**超宽表**（数百列）时序数据的处理上，
如何高效完成列转行（explode）并保持作业的可维护性，
仍是一个值得工程化解决的问题。

本课题在实测中发现，宽表转长若使用 Hive 的 `stack()` 函数
需硬编码全部列名，新增指标必须修改 SQL 并重新编译；
而使用 MapReduce 动态遍历列可实现"新增指标零代码改动"，
这一对比分析本身即构成了一项工程实践层面的贡献。

### 1.2.3 研究现状小结与本课题定位

综合来看，现有研究存在三点可改进空间：

1. **数据可复现性不足** —— 公开的充电设施运行数据稀缺，研究结论难以复现验证
2. **分析粒度偏宏观** —— 多聚焦于城市或区域总量，缺少分区级的精细化供需刻画
3. **价格因素考虑不足** —— 较少有研究利用分时电价机制，量化其对充电行为的引导效果

**本课题的定位**：以公开发布的高粒度真实数据集为对象，
构建可完整复现的四层数仓分析系统，
并在分析层提出三个具有业务解释力的量化指标，
将理论方法与工程实现结合。

## 1.3 研究内容与主要工作

本课题的主要工作包括以下五个方面：

**（1）数据接入与采集**
设计基于 Flume 的增量采集方案，实现 UrbanEV 原始 CSV 数据到 HDFS 的自动接入，
并建立数据校验机制确保采集完整性。

**（2）离线数据仓库构建**
设计并实现 ODS-DWD-DWS-ADS 四层数据仓库模型。
其中 ODS 层保留源数据宽表原貌，
DWD 层通过 MapReduce 完成**宽表转长**与质量清洗，
DWS 层完成分区-日-小时粒度的多指标汇总，
ADS 层按"一张表对应一个前端图表"的原则组织应用指标。

**（3）分析指标体系构建**
设计 12 项基础分析指标与 3 个创新指标体系，涵盖规模、强度、价格、供需匹配四个维度。

**（4）在线服务与可视化**
基于 Spring Boot 构建 RESTful 服务层，
结合 MySQL 与 Redis 实现数据存储与热点缓存，
基于 ECharts 构建可交互的数据分析看板。

**（5）系统集成与可复现性**
通过 Docker Compose 实现一键编排部署，
提供端到端冒烟测试脚本与完整运行手册，确保系统可被独立复现。

# 第二章 需求分析

## 2.1 可行性分析

### 2.1.1 技术可行性

**（1）数据可得性**

本课题选用的 UrbanEV 数据集由中山大学 Han Li 与香港理工大学 Haohao Qu 联合发布，
采用 CC0 1.0 Universal 公共领域许可，
可通过 GitHub 公开仓库直接获取，
包含深圳 275 个交通分区、23,441 个充电桩、
2022 年 9 月至 2023 年 2 月共 4,344 个逐小时时点的运行数据，
以及 71 万条兴趣点数据。
数据规模与粒度完全满足四层数仓建模与多维聚合分析的要求。

**（2）技术栈成熟度**

系统采用的 Hadoop 3.3.6、Hive 4.0.0、Spark 3.4、Flume 1.11、Sqoop 1.4.7
均为 Apache 顶级项目的稳定版本，官方文档完善、社区活跃。
后端采用的 Spring Boot 3.2.5 与前端 ECharts 5 同样是成熟稳定的技术选择。
关键技术点（宽表 explode、空间连接、时序聚合）均有大量公开实践参考。

**（3）计算资源需求**

经估算，原始层约 120 万个数据单元格，长表化后约 717 万行，
ADS 层聚合计算的数据量在千万级以内。
该规模在单机 Docker 环境的资源占用下（建议 8GB 内存以上）可稳定运行，
不存在资源瓶颈。

**（4）技术风险与应对**

| 风险 | 影响 | 应对措施 |
|---|---|---|
| 宽表列数多，代码维护困难 | DWD 层开发受阻 | 采用 MapReduce 动态遍历列，新指标零代码改动 |
| POI 数据量大，空间连接慢 | 计算耗时超预期 | Map 端加载分区坐标（广播），避免笛卡尔积 |
| 集群环境配置复杂 | 演示失败 | Docker Compose 一键编排 + 三层自动降级策略 |
| 答辩现场网络或环境异常 | 无法演示 | 预录 5-8 分钟演示视频作为兜底 |

### 2.1.2 经济可行性

本课题使用全部开源软件（Apache 协议）与公开数据集（CC0 协议），
**软件与数据成本均为零**。
系统采用 Docker Compose 部署于个人笔记本，
无需额外采购服务器或云服务。
开发周期内主要投入为团队成员的时间成本。
因此本课题在经济上完全可行。

### 2.1.3 操作可行性

系统采用 B/S 架构，用户通过浏览器访问，
无需安装客户端。界面采用深色主题的决策看板形式，
提供日期范围、时段、分区、电价类型四个维度的交互筛选，
符合运营人员与管理人员的使用习惯。

## 2.3 系统非功能需求

### 2.3.1 性能需求

| 指标 | 要求 | 实现方式 |
|---|---|---|
| 首页聚合查询响应 | ≤ 500 ms | Redis 缓存首页聚合结果，TTL 300s |
| 明细指标查询响应 | ≤ 1 s | MySQL 索引优化 + MyBatis 缓存 |
| 复杂图表查询响应 | ≤ 2 s | ADS 层预聚合 + 结果缓存 |
| Hive 四层全链路计算 | ≤ 30 min | Spark on local[*] + 分区裁剪 |
| 系统可用性 | ≥ 99% | Docker 健康检查 + 自动重启策略 |

### 2.3.2 可靠性需求

- **数据完整性**：采集环节提供校验脚本，验证文件数量与行数；
  计算环节通过四层表 `COUNT(*)` 对比验证（要求 DWD 行数少于 ODS 行数，以证明清洗真实生效）
- **服务健壮性**：全局异常处理器统一异常响应格式，避免异常堆栈泄露；
  Redis 与 MySQL 连接均配置超时与重连
- **可复现性**：提供一键部署脚本与冒烟测试，
  确保第三方可在独立环境中复现系统运行

### 2.3.3 可维护性与可扩展性需求

- **分层解耦**：数据接入、数仓计算、分析建模、服务呈现四层职责清晰，层间通过契约文件约定接口
- **配置外置**：数据库地址、缓存配置等全部通过环境变量注入，切换环境无需修改代码
- **指标可扩展**：ADS 层新增指标只需新增 SQL 与表，不影响已有模块
- **文档完备**：提供数据字典、指标定义表、接口规范、数仓表结构规范四份契约文档与运行手册

### 2.3.4 安全性需求

本系统为课程作业原型，运行于本地环境。
账号密码采用配置文件管理而非硬编码，
所有数据库访问通过参数化查询避免 SQL 注入，
后端接口统一配置异常处理，避免内部信息泄露。
生产环境部署时需进一步引入身份认证、HTTPS 传输加密与操作审计。
