### 2.1.2 为什么后端用 JDK 17 而 Hive 4.0 镜像用 JDK 8

这是本项目工具链中一处**真实存在且必须解释**的版本差异。

`backend/pom.xml` 第 9 行明确写"依赖版本已按 Java 17 + Spring Boot 3.2.5 对齐，不要随意升级大版本"。
这一约束由 Spring Boot 3.x 自身强制：Spring Boot 3 要求 **JDK 17 作为最低基线**，
且 Jakarta EE 命名空间（`jakarta.servlet.*`）在 JDK 8 上完全不可用。
《RUNBOOK》§2.3 给出的原生部署方案亦将 `JAVA_HOME` 指向 `java-17`。

而 Hive 4.0.0 的官方镜像 `apache/hive:4.0.0` 内置的是 **JDK 8** 运行时。
这一差异不是本项目的疏忽，而是 Apache Hive 4.0 发行版自身的构建选择。
它在本项目中造成了一个**必须被隔离的技术冲突**——
`pom.xml` 第 106–119 行的注释把这条冲突及解决方案完整记录了下来：

> `hive-jdbc` 3.1.3 的传递依赖里有 `jdk.tools:jdk.tools:1.6`（system scope），
> 那是 **JDK 8 的产物**，在 **JDK 17 下已移除**，会导致
> "Could not find artifact jdk.tools:jdk.tools:jar:1.6" 而构建失败。

换言之：**Hive 侧的 JDBC 驱动按 JDK 8 生态打包，而本项目的后端必须跑在 JDK 17 上**，
两者直接放进同一个 classpath 会在编译期就炸掉。

本项目采取的解法是**把 Hive JDBC 做成可选 profile**，在 `pom.xml` 第 120–141 行定义为 `hive` profile，
并显式 `<exclusions>` 掉 `jdk.tools` 与 `slf4j-log4j12`：

```xml
mvn clean package          → 默认构建（不含 hive-jdbc，快）
mvn clean package -Phive   → 需要直连 Hive 时启用
```

这个设计的巧妙之处在于**本系统根本不需要连 Hive**：
`pom.xml` 第 113 行指出"本系统后端的 16 个接口全部基于 MySQL 视图查询，不需要连 Hive"。
因此把 Hive JDBC 隔离到可选 profile，既消除了构建冲突，
又让默认构建不受 `hadoop-common` / `guava` / `netty` 等传递依赖的版本冲突拖累——
按注释估算，首次构建可节省 3–5 分钟。

> **本节的结论**：JDK 17 与 JDK 8 的版本差异不是妥协，而是**通过构建期隔离**消除的：
> 后端编译期用 JDK 17 且完全不引入 Hive 驱动；Hive 侧以独立容器运行 JDK 8 镜像，
> 二者通过 HiveServer2 的 JDBC 端口（10000）在**运行期**而非编译期解耦。

### 2.1.3 容器化编排：一个文件管理 11 个服务、6 组 profile、14 个卷

`docker-compose.yml` 是全系统部署的单一入口，它定义了 **11 个服务**、
**6 组 profile**（`base` / `app` / `hadoop` / `hive` / `spark` / `full`）与 **14 个命名卷**。

**表 2-2 docker-compose 服务与 profile 归属表**

| profile | 启动的服务 | 覆盖能力 |
|---|---|---|
| `base` | mysql、redis | 仅数据与缓存底座 |
| `app` | base + backend、frontend | 仅应用层（本机已有 Hadoop 时用） |
| `hadoop` | namenode、datanode、resourcemanager、nodemanager、flume | 大数据底座 |
| `hive` | hive（HiveServer2 + 内嵌 Derby Metastore） | 数仓查询层 |
| `spark` | spark（独立 Spark Master） | DWS / ADS 计算层 |
| `full` | 以上全部 | 完整全链路（答辩演示用） |

profile 机制的价值在于**降级**：《RUNBOOK》§三给出的启动方式是 `bash scripts/start_all.sh`，
脚本会自动探测环境并选择 full / app / native 三种模式，
从而做到"别人拿到仓库 30 分钟内跑起来"。

这份编排文件本身也是一份**踩坑记录**。compose 第 20–26 行记录了一个曾让整套集群配置静默失效的坑：

> ⚠️ 之前误写成 `CORE_SITE_CONF: >- fs.defaultFS=...`，解析器按 `[_\.]` 切分后得到
> name=core / ext=site，site 不在白名单 → **配置被静默丢弃**，
> `fs.defaultFS` 一直保持默认，整套集群配置根本没生效。已于 11/20 修正。

修正后的写法是官方镜像约定的 `CORE-SITE.XML_fs.defaultFS` 形式。
此外 compose 第 112–116 行说明"每个服务独立 conf 卷 —— 之前 4 个容器共用 hadoop-conf 互相覆盖配置"，
第 400–401 行说明"HDFS 持久化 —— 之前数据在容器 /tmp，每次 up 重新 format → 数据全丢"。
这些注释的价值在于：**它们把"为什么代码写成这样"固化在了代码旁边**，
使得后续维护者不需要重新踩一遍坑才能理解当前的写法。

### 2.2.1 双语言分工

本系统使用 **Java** 与 **Python** 两种语言，分工边界清晰，不是"顺手用了两种"。

**表 2-3 Java 与 Python 的职责分工**

| 维度 | Java 17 | Python 3.13 |
|---|---|---|
| 承担模块 | Spring Boot 后端服务、3 个 MapReduce 作业 | `python_etl.py` ETL 兜底管道、DDL 生成脚本、样例导出脚本、Flume 配置验证脚本 |
| 关键源码 | `HealthController.java`、`Result.java`、`GlobalExceptionHandler.java`、`RedisConfig.java`、`WideToLong.java`、`DataQualityCheck.java`、`PoiZoneJoin.java` | `scripts/python_etl.py`（703 行）、`scripts/gen_ods_ddl.py`、`scripts/export_samples.py`、`scripts/verify_flume_config.py` |
| 依赖生态 | Spring Boot 3.2.5、MyBatis 3.0.3、Hadoop Client API | pandas、numpy、scikit-learn（`RandomForestRegressor`、`LinearRegression`） |
| 运行环境 | Tomcat 10.1.20 内嵌容器 / `eclipse-temurin:17-jre-alpine` | 本机 CPython 3.13.14 |
| 部署形态 | 打进 `uev-charge-analysis.jar`（约 37 MB），容器内运行 | 宿主机直接执行 `python scripts/python_etl.py` |

### 2.2.2 为什么是双语言

**Java 承担后端与 MapReduce**，理由有三：其一，MapReduce 作业必须用 Java——
`hadoop/mr/` 下的三个作业直接 import `org.apache.hadoop.mapreduce.*`，
且 Map 端广播 275 个分区中心点这类优化只有在 JVM 上才有对应的 `setup()` 生命周期钩子可用；
其二，课程目标是 Java Web 后端，后端服务理应使用 Java；
其三，`WideToLong` 用 Java 而非 Hive SQL 的理由写在《04-数仓表结构规范》§4.2：
Hive 的 `stack()` 要硬编码 275 个列名，**新增指标必须改 SQL 并重新编译**，
而 MapReduce 动态遍历所有列可做到"新增指标零代码改动"。

**Python 承担分析与兜底**，理由同样具体：
`python_etl.py` 的文件头注释（"为什么有这个脚本"一节）写明，
它的第一职责是**兜底**——保证"报告里所有指标都有可核对的真实数字，而不是空表或编造值"；
第二职责是**可复现**——它本身就是"一键复现部署"的第四条路径；
第三职责是**口径校验**——"用 Python 独立实现一遍指标公式，与 Hive SQL 的结果可交叉比对，
这正是报告 6.3「数据准确性测试」所要求的验证方式"。

值得注意的是 Python 在本项目中承担的不只是"脚本"角色：
`python_etl.py` 第 501–522 行的模型竞优部分**完整实现了三个模型的训练、预测与评估**
（`RandomForestRegressor(n_estimators=40, max_depth=10, random_state=42, n_jobs=-1)`、
`LinearRegression`、以及作为基线的 lag1），
并输出了《实测数据附表》第五节的三模型对比结果。
这段代码位于一个 `.py` 文件中而非 Java 侧，正是因为 pandas / numpy / scikit-learn
在表格化时序数据上的表达力远高于 Java。

> **本节的结论**：双语言的边界由**计算形态**划定——
> 需要 JVM 生态与 Hadoop 生命周期的部分用 Java，需要表格化数据科学与快速数值实验的部分用 Python，
> 二者通过《02-指标定义表》这一份共享公式契约保证口径一致。

## 2.3 Hadoop 生态

本节逐一说明 HDFS、MapReduce、YARN、Flume、Sqoop 五个组件
**在本项目具体承担哪一步工序**，而非泛泛介绍其功能。

### 2.3.1 HDFS：原始数据与数仓的落地层

HDFS 在本项目中承担**两段**存储职责，且两段的目录结构完全不同。

**第一段是 ODS 原始层**：`/uev/raw/<数据集名>/` 下的 **12 个独立子目录**，
与 `uev_ods.*` 的 12 张贴源表一一对应。
这一"一表一目录"的结构是 Flume 配置的设计目标（详见 2.3.4），
《RUNBOOK》§四步骤 6 逐行列出了 12 个目录到 ODS 表的映射关系。

**第二段是数仓计算层**：`/uev/dwd/long/<指标名>`（宽转长输出）、
`/uev/dwd/dq/<指标名>`（质检输出）、`/uev/dwd/zone_poi_count`（空间连接输出）。
这三个路径分别对应《RUNBOOK》§四步骤 7.2 / 7.3 / 7.4 三条 `hadoop jar` 命令的输出参数。

HDFS 的副本策略在本项目中简化为 **1 份**（compose 第 96 行 `HDFS-SITE.XML_dfs.replication: "1"`），
这是单机伪分布式环境的必然选择——多副本在单 DataNode 上不产生实际容错收益，
反而浪费磁盘。《RUNBOOK》§二给出的 20 GB 磁盘门槛正是基于这一配置测算的。

### 2.3.2 MapReduce：三个作业，承担三类重计算

`hadoop/mr/` 目录下有三个 Java 作业，各自承担一类计算。
它们是本系统"数据是宽表不是长表"这一核心难点的直接产物。

**表 2-4 三个 MapReduce 作业的职责与参数**

| 作业类 | 承担工序 | 输入 → 输出 | 关键实现 | 可调参数 |
|---|---|---|---|---|
| `com.uev.mr.WideToLong` | **宽转长**（276 列 → 标准长表） | `/uev/raw/<指标>/` → `/uev/dwd/long/<指标>` | Mapper 动态遍历 275 个分区列，每列输出一行 | `-D uev.metric.name=<指标名>` |
| `com.uev.mr.DataQualityCheck` | **数据质量检查**（8 类规则） | `/uev/raw/<指标>/` → `/uev/dwd/dq/<指标>` | 逐单元格判定越界/零值/重复时间戳 | `-D uev.metric.name` `-D uev.metric.min` `-D uev.metric.max` |
| `com.uev.mr.PoiZoneJoin` | **POI 空间连接** | `/uev/raw/poi/` + `inf` → `/uev/dwd/zone_poi_count` | `setup()` 加载 275 个分区中心点到内存（广播），逐条 POI 算 Haversine 球面距离 | `-D uev.zone.info.path=/uev/raw/inf/` |

三个作业中有两处值得展开的实现细节：

**其一，`WideToLong` 的末尾空列处理。** 源码第 77 行的注释写明：
`// 用 -1 保留末尾空列，避免最后一个分区被丢掉`。
这是一个极易忽略的边界条件——若不保留末尾空列，275 个分区中的最后一个会静默丢失，
而丢失一个分区在总计 717 万行的量级下**几乎不可能被察觉**，
只会在后续按分区聚合时表现为"某个分区数据莫名偏少"。

**其二，`DataQualityCheck` 的单 Reducer 汇总。** 源码第 160 行明确：
`job.setNumReduceTasks(1);   // 质量统计用单 Reducer 汇总最方便`。
质量统计需要全局聚合（某指标全量有多少越界值），单 Reducer 直接输出即可，
避免了 shuffle 开销。

**其三，`PoiZoneJoin` 的 Map 端广播。** 源码第 42–43 行注释写明：
"分区坐标表只有 275 行，直接在 setup() 里加载到内存（广播）"。
这一步把 712,135 × 275 ≈ **1.96 亿次**笛卡尔积的距离计算，
降为 712,135 次"与 275 个候选分区"的比较——《RUNBOOK》附录 E 的问答里
把这一优化列为应对"POI 数据量大、空间连接慢"风险的具体措施。

### 2.3.3 YARN：资源调度层

YARN 在本项目中承担 Hadoop 作业的资源分配与容器隔离。
《RUNBOOK》§1.3 端口一览中列出的 **8088 端口（YARN Web UI）**
与 **9870 端口（NameNode Web UI）** 正是答辩演示时展示集群状态的两个入口。

配置层面，compose 第 104–107 行为 NodeManager 设定了资源上限：
`yarn.nodemanager.resource.memory-mb: "2048"`、`vcores: "2"`，
调度器最小分配 512 MB / 最大 2048 MB。
这个 2 GB 的 NodeManager 内存上限是**可解释的**：
Spark 在 `local[*]` 模式下与三个 MR 作业共享同一个 NodeManager，
其中 `PoiZoneJoin` 需要在 Map 端常驻 275 个分区中心点，
内存设定过小会导致 Map 任务反复重试。

### 2.3.5 Sqoop：Hive ADS → MySQL 的交换层

Sqoop 承担数仓结果向业务库的导出。《RUNBOOK》§四步骤 9 给出的命令形如：

```bash
docker exec uev-namenode sqoop export \
  --connect jdbc:mysql://mysql:3306/uev_charge \
  --table zone_occupancy \
  --hcatalog-table uev_ads.zone_occupancy \
  --hcatalog-database uev_ads \
  --hive-import -m 1 \
  --null-string '\\N' --null-non-string '\\N'
```

其中 `--hcatalog-table` 而非 `--table` 的写法是关键：它直接按 Hive 元数据列名与类型映射，
避免手工维护 MySQL 列名与 Hive 列名的对应表。

《RUNBOOK》在该节标注了**两个必须绕开的坑**：
其一，`apache/hadoop` 镜像不含 sqoop，需在装好 sqoop 的环境里跑；
其二，`apache/sqoop:1.4.7` 自带的 `mysql-connector-java 5.1.x` 连 MySQL 8 会报
`Unknown system variable 'query_cache_size'`，**必须换成 connector 8.x**。
文档同时给出了推荐的兜底路径：`Hive → CSV → MySQL LOAD DATA LOCAL INFILE`。

另有一处类型映射的细节被固化在《RUNBOOK》附录 C：
Hive 的 `TIMESTAMP` 类型在 MySQL 侧用 **`VARCHAR(30)`** 接收，
理由是"用字符串避免映射坑"。这与 `db/mysql/01_schema.sql` 第 15–16 行的注释完全一致——
"Sqoop 导出时 compute_time 等时间字段用 VARCHAR 存字符串，
避免 Hive TIMESTAMP → MySQL DATETIME 的类型映射坑"。

### 2.4.1 MySQL 8.0：面向服务的应用库

MySQL 在本项目中承担**在线服务的数据出口**角色，业务库名 `uev_charge`，
字符集 `utf8mb4`、引擎 InnoDB（`db/mysql/01_schema.sql` 第 19–21 行）。
《04-数仓表结构规范》§七与 `db/mysql/01_schema.sql` 共同定义了 **19 张表与视图**，
按前缀分为四类：

| `ads_*` | 7 | B（苏静） | Sqoop export（由 Hive ADS 落地） | D（经视图） | 面向图表的应用指标，与 `uev_ads.*` 一一对应 |

### 2.4.2 Hive 4.0.0：四层数据仓库

Hive 承担**离线加工与分层建模**。
《04-数仓表结构规范》第一章明确了四层职责：

| 层 | 职责 | 谁看 |
|---|---|---|
| **ODS** | 贴源存放，**保留宽表原貌**（275 列），不做任何加工 | 苏静 |
| **DWD** | **宽转长 + 清洗 + 补齐维度**：一行 = 一个分区在一个小时的一个指标 | 苏静 / 姬婷婷 |
| **DWS** | 轻度汇总：按天聚合、滚动均值、峰谷标识、分区供给画像 | 苏静 / 姬婷婷 |
| **ADS** | 应用指标层：**一张表对应前端一个图表** | 苏静 / 杨姗姗 / 贺欢欢 |

全库共 **16 张建模表**（DWD 4 张 + DWS 4 张 + ADS 8 张）。
ODS 层的贴源表由 `hadoop/hive/gen_ddl.py` 依 CSV 表头**自动生成 DDL**——
《01-数据字典》§5.1 明确指出"275 列手写不现实"，必须用脚本生成。

存储格式上，DWD / DWS / ADS 层统一采用 **ORC + SNAPPY 压缩**
（`TBLPROPERTIES ('orc.compress'='SNAPPY')`），分区键统一为 `dt`（`yyyy-MM-dd`）。
DWD 主表 `uev_dwd.zone_hour_metric` 的字段为
`zone_id / hour_ts / hour_of_day / day_of_week / metric / value / is_zero`（7 个业务字段 + 1 个分区键），
`metric` 的取值为 `occupancy` / `duration` / `volume` / `volume_11kw` / `e_price` / `s_price` 六种。

值得强调的是《04-数仓表结构规范》开篇那句判断：
"本项目数仓的核心技术点就在 ODS → DWD 这一步：宽表 explode 成标准长表。"
这一层的技术难度决定了《03-接口规范》与《02-指标定义表》都必须以长表字段名为准——
契约 02 的变更记录第 v1.0 条目写明"按实测数据修正表名与字段"，正是这次修正的依据。

### 2.4.3 为什么既有 MySQL 又有 Hive

两套数据库并存**不是技术冗余，而是职责切分的结果**。
《04-数仓表结构规范》给出的三条理由构成完整论证：

**第一，Hive 承担 MySQL 做不到的加工形态。** 原始数据是 `time` + 275 个分区列的宽表，
无法直接按 `zone_id` 分组聚合；而 MySQL 没有 Hive `LATERAL VIEW stack()` 的等价物，
只能按分区竖切成 275 张窄表再 `UNION ALL`，代码量与维护成本急剧上升。

**第二，Hive 承担迭代型分析。** 电价 σ 反推 TOU 分区 → 失衡指数 → 分区类型分组 → 预测回测，
这四轮迭代若每轮都回读原始宽表，I/O 会成倍放大；
Hive 的分区裁剪（`WHERE dt BETWEEN ...`）让每一轮只扫描需要的日期区间。

**第三，MySQL 承担 Hive 做不到的在线服务。** 本系统对前端暴露的 16 个 REST 接口
全部是**高频、并发、要求毫秒级响应**的只读查询。
Hive 的查询延迟在秒级且难以承载并发，不适合做在线接口的数据源；
而 ADS 表的数据量已被预聚合到极小规模——实测 `dashboard_kpi` 仅 **1 行**、
`zone_occupancy` **275 行**、`hourly_supply_demand` **24 行**、
`imbalance_index` **200 行**、`price_elasticity` **24 行**、
`demand_forecast` **3,850 行**、`expansion_suggestion` **167 行**，
合计不足 5 千行，完全适合放在 MySQL 里被反复查询。

> **本节的结论**：Hive 是**加工场**，MySQL 是**服务台**——
> 数据在 Hive 里被反复变形与聚合，最终凝固为 ADS 层的 7 张小表，
> 再经 Sqoop 落地 MySQL 并由 4 张视图联查，最终由 16 个接口对外供给。

### 2.5.1 Spring Boot 3.2.5

后端以 `spring-boot-starter-parent` **3.2.5** 为父 POM（`pom.xml` 第 33–38 行），
共声明 9 个直接依赖：web、validation、mysql-connector-j、mybatis-spring-boot-starter、

选型要点有三：

理由已在 2.1.2 节详述——它是本项目唯一的 JDK 版本冲突源，

构建产物经 `spring-boot-maven-plugin` 打成**可执行 fat jar**，

阶段二用 `eclipse-temurin:17-jre-alpine` 运行。
阶段一的 `COPY pom.xml .` + `mvn dependency:go-offline` 是**依赖预热**，
利用 Docker 层缓存使"改代码不用重下依赖"；阶段二仅 200 MB 镜像，
配合 Dockerfile 注释所说的"镜像小、启动快，答辩现场拉取快"。

### 2.5.2 MyBatis 3.0.3 与「MyBatis 还是 MyBatis-Plus」

**`pom.xml` 第 72–77 行是本项目的权威声明**：

```xml
<!-- MyBatis（不用 JPA，因为 ADS 层表结构是宽表，SQL 控制更直接） -->
<dependency>
    <groupId>org.mybatis.spring.boot</groupId>
    <artifactId>mybatis-spring-boot-starter</artifactId>
    <version>${mybatis.version}</version>   <!-- ${mybatis.version} = 3.0.3 -->
</dependency>
```

这是**纯 MyBatis**，坐标 `org.mybatis.spring.boot:mybatis-spring-boot-starter:3.0.3`，
不含任何 `com.baomidou` 依赖。

**为什么不用 JPA**，注释给出了明确理由："ADS 层表结构是宽表，SQL 控制更直接"。
这一判断与数据形态吻合：本系统的 ADS 层是 7 张**固定的、字段明确的小表**，
不需要 JPA 的对象关系映射与懒加载，反而需要精确控制聚合 SQL 与索引使用。

**为什么不用 MyBatis-Plus**，`pom.xml` 第 19–26 行的注释给出了一条**极其实用的警告**：

> ★ 如果你要用 MyBatis-Plus（而不是 MyBatis），必须换成 SB3 专用坐标：
> `com.baomidou:mybatis-plus-spring-boot3-starter:3.5.5`
> 注意 artifactId 必须是 `mybatis-plus-spring-boot3-starter`（带 spring-boot3），
> 用 `mybatis-plus-boot-starter` 在 Spring Boot 3 下会启动失败。

这条注释的价值在于它把一个**极易踩且极难查**的坑固化在了配置旁边：
`mybatis-plus-boot-starter` 与 `mybatis-plus-spring-boot3-starter` 只差几个字符，
但后者才是 Spring Boot 3 的正确坐标，选错会在启动期直接失败。

**因此本项目的口径是：以 `pom.xml` 为准，使用纯 MyBatis 3.0.3。**
`README.md` 第 71 行的"MyBatis-Plus"表述属于文档滞后，应在后续修订中更正。

`application.yml` 第 63–70 行给出了 MyBatis 的具体配置：
`mapper-locations: classpath:mapper/*.xml`、`type-aliases-package: com.uev.mapper`、
`map-underscore-to-camel-case: true`（**下划线转驼峰**，
这正是《03-接口规范》要求字段名"大小写敏感"一致的技术基础）、
`default-fetch-size: 500`、`default-statement-timeout: 30`（**30 秒语句超时**）。

### 2.5.3 Redis 7 缓存层

Redis 承担三类接口的结果缓存。《03-接口规范》§1.4 规定了分层 TTL：

| 接口类型 | 缓存 key | TTL |
|---|---|---|
| `/dashboard/kpi` | `uev:kpi:{hash}` | 300 秒 |
| `/zones/occupancy` | `uev:zone_occ:{hash}` | 600 秒 |
| `/charts/*` | `uev:chart:{name}:{hash}` | 120 秒 |

`application.yml` 第 79–84 行把 TTL 化为可配置项：
`uev.cache.dashboard-ttl: 300`、`filter-ttl: 120`、`chart-ttl: 600`，
与契约中的数值一一对应。

> 🔴 **缓存设计上最关键的一条约束**，《03-接口规范》§1.4 用加粗强调：
> "缓存 key 要包含全部筛选参数（用参数哈希），否则改筛选条件会拿到旧数据——这是最常见的缓存 bug。"

这条约束在源码里有对应实现。`RedisConfig.java` 定义了 `KEY_PREFIX = "uev:"` 常量，
注释写明"键统一加 `uev:` 前缀，便于清理和排查"，
与上表三类 key 的前缀完全对应。
序列化方面，`RedisConfig` 第 41–48 行做了三件事：
Key 与 HashKey 用 `StringRedisSerializer`（保证 `redis-cli` 可直接读、可手工清理）；
Value 用 `Jackson2JsonRedisSerializer`，其 `ObjectMapper` 注册了 `JavaTimeModule`
（支持 `LocalDateTime` 序列化）并调用 `activateDefaultTyping(..., NON_FINAL)`
（保留类型信息，保证反序列化后仍为原类型）。

### 2.5.4 统一响应与全局异常处理

`common/Result.java` 定义了全系统统一的响应结构 `{code, message, data, timestamp}`，
字段含义与《03-接口规范》§1.2 完全一致。
其静态工厂方法覆盖了 200 / 400 / 404 / 500 四种状态码，
`timestamp` 在**构造时**由 `System.currentTimeMillis()` 自动填入——
这保证了每个响应的时间戳都是服务端真实发出时刻，而非某个被复用的常量。

`common/GlobalExceptionHandler.java` 用 `@RestControllerAdvice` 注册了三个处理器：

| 捕获异常 | HTTP 状态 | 响应 message | 源码行号 |
|---|---|---|---|
| `IllegalArgumentException` | **400** | `"参数错误: " + e.getMessage()` | 23–28 |
| `ResourceNotFoundException` | **404** | `e.getMessage()` | 31–36 |
| `Exception`（兜底） | **500** | `"系统内部错误，请查看后端日志"` | 39–44 |

兜底处理器的设计意图在类注释里写得很直白：
"把后端异常统一转成 Result 结构，前端只需判断 code，不用解析异常栈。"
《03-接口规范》§1.2 的前端约定正是"只判断 `code === 200`，不解析异常栈"——
**后端的设计精确对齐了前端的使用方式**，这不是巧合，而是契约驱动的直接结果。

### 2.5.5 健康检查：把"系统是否可用"变成一个可编程的接口

`controller/HealthController.java` 是目前**唯一已实现**的业务 Controller
（`scripts/check-contracts.sh` 的第 3 项检查中，11 个契约接口里只有 `/api/health` 报"已实现"）。

它做了一件比"返回 200"更多的事：**逐个探测依赖组件的真实连通性**，
并把探测结果结构化：

- `checkMysql()`：取一个 `Connection` 并执行 `SELECT 1`，
  返回值为 1 才判 `"UP"`，异常时记 `log.warn` 并返回 `"DOWN"`；
- `checkRedis()`：调用 `redisTemplate.getConnectionFactory().getConnection().ping()`，
  返回 `"PONG"` 才判 `"UP"`；
- 两者**有一个不是 UP**，整体 `status` 就从 `"UP"` 降级为 **`"DEGRADED"`**（第 71–75 行）。

这个设计对答辩场景价值很高：前端右上角的 `sysStatus` 指示器
（`frontend/index.html` 第 19 行 `<span class="status" id="sysStatus">检测中…</span>`）
可以直接反映"后端活着但数据库连不上"这种**部分故障**，
而不是笼统的"打不开"。

`regionCount` 通过 `@Value("${uev.data.region-count:275}")` 注入，
`application.yml` 第 91 行配置为 `${DATA_REGION_COUNT:275}`，
compose 第 363 行通过 `DATA_REGION_COUNT` 环境变量注入——
三级兜底保证分区数口径恒为 **275**。
这正是《03-接口规范》§2.1 特别提醒"默认值 96 需在 application.yml 中改为 275"的那一项。

## 2.6 数据可视化技术

### 2.6.1 ECharts 5 与原生 JavaScript

前端不使用任何前端框架与构建工具，采用 **ECharts 5 + 原生 JavaScript** 的组合
（`frontend/` 目录下共 9 个文件：`index.html`、`Dockerfile`、`nginx.conf`、
`js/{common,app,echarts.min}.js`、`css/style.css`、
`assets/{shenzhen_440300_full.json, 底图使用指引.md}`）。
《RUNBOOK》§1.1 技术栈表把前端一行写为"ECharts 5 + 原生 JS — 数据看板"。

选择原生 JS 而非 Vue / React 的理由，与《03-接口规范》§三的前端映射表直接相关：
前端骨架 `frontend/js/app.js` 已按契约写好 7 个加载函数
（`loadKpi`、`loadHeatmap`、`loadHourly`、`loadImbalance`、
`loadPriceElasticity`、`loadForecast`、`loadSuggestion`），
共 9 个函数定义（含 `loadAll` 与 `loadBaseMap`）。
这些函数以 `async/await` + `fetch` 组织，
通过 `common.js` 封装的 `apiGet(path, params)` 统一发请求——
引入框架反而需要重写这套骨架。

### 2.6.2 为什么必须本地化 ECharts

**ECharts 必须本地化，这是本项目的一条硬性约束，不是可选项。**
`scripts/smoke_test.sh` 第 279–283 行把它列为**失败项**而非警告项：

```bash
if [ -f "frontend/js/echarts.min.js" ]; then
  pass "echarts.min.js 已本地化（答辩现场无网可用）"
else
  fail "echarts.min.js 缺失 —— 必须在答辩前本地化，不能依赖 CDN"
fi
```

理由在《RUNBOOK》§8.3"答辩现场应急"表中写得很明确：
答辩现场可能断网，而 ECharts 是**全站唯一的图表渲染引擎**——
一旦 CDN 不可达，6 张图表、5 个 KPI 卡与分区地图将全部无法渲染，
整个系统的可视化部分直接归零。

本地化的实际规模：`frontend/js/echarts.min.js` 为 **1,029,203 字节（约 1.03 MB）**，
`frontend/assets/shenzhen_440300_full.json` 为 **69,077 字节（约 69 KB）**，
两者合计约 1.1 MB。`index.html` 第 164–166 行以三个 `<script>` 标签按序引入
`echarts.min.js` → `common.js` → `app.js`，全部为**同源相对路径**，无任何外部域名引用。

深圳底图 GeoJSON 同样本地化。`app.js` 的 `loadBaseMap()` 加载它并注册为 ECharts 地图，
源码注释同时说明了一个重要的口径边界：
"底图是深圳市 9 个行政区，而数据是 275 个交通分区，
两者是不同划分体系。本系统用经纬度定位散点，不做分区与行政区的对应。"
这条说明直接回应了《01-数据字典》中"inf.csv 行序 ≠ 时序表列序"同源的坑——
**分区与行政区是两个体系，任何按位置对齐的做法都会失真**。

### 2.6.3 深色主题与统一视觉语言

`common.js` 定义了 `CHART_COLORS` 调色板与 `baseOption()` 基础配置，
《03-接口规范》§2.6 的注释写明"summary 是给 PPT 用的：前端把它显示在图表标题右侧"，
即电价弹性的 TOU / FLAT 峰谷差会直接显示在图标题旁，
便于答辩时口述"TOU 组 0.21，FLAT 组 0.35"。
《第 3–4 章初稿》也提到深色主题是"答辩投影友好"的刻意选择。

### 2.6.4 交互与容错

前端支持 **4 个筛选维度**（日期范围、时段、分区、电价类型）的联动刷新，
`app.js` 的 `loadAll()` 函数一次性并发调用 7 个加载函数：

```javascript
await Promise.all([
    loadKpi(f), loadHeatmap(f), loadHourly(f), loadImbalance(f),
    loadPriceElasticity(f), loadForecast(f), loadSuggestion(f)
]);
```

容错方面，`common.js` 的 `safeQuery(fn, errTarget)` 包装了每个请求：
出错时在目标容器内渲染"⚠ 数据加载失败：{message}"并提示
"请确认后端已启动（bash scripts/start_all.sh）"，
**不让页面白屏**。《RUNBOOK》§三也确认了这一点：
"如果只想看前端效果但没有后端数据，前端会显示'数据加载失败'的占位提示，
但版式、图表框架、筛选交互都能看到——可以先做 PPT 版式。"

> **本节的结论**：可视化的技术选型服务于**两个具体约束**——
> 离线可用（本地化 ECharts 与 GeoJSON，冒烟脚本把缺失判为 fail）与
> 契约对齐（7 个加载函数严格对应《03-接口规范》§三的映射表），
> 二者共同保证了答辩现场"即使后端挂了，版式与交互仍然可见"。

### 2.7.2 两条计算路径在 MySQL 汇合的设计

这是本系统架构层面最需要解释的一处设计。

**问题的由来是交付节奏**。《04-数仓表结构规范》与第 3–4 章初稿记录了三条理由：

1. **解耦时间依赖** —— E 岗的交付节点早于 B 岗的 Sqoop 导出节点，
   若强制 E 走 Hive → Sqoop 链路会产生**时间倒挂**；改为直插后两条路径完全并行。
2. **不牺牲核心创新点的可控性** —— 创新点④的聚类本就要写自己的 MLlib 代码，
   塞进 B 的 Spark 脚本等于把核心工作交给他人执行。
3. **口径一致性仍可保障** —— 两条路径都以《02-指标定义表》为唯一公式来源，
   并在报告 6.3 节做"同一指标 MySQL 查询值 = Hive 直查值"的逐项校验。

**汇合点被刻意放在视图层**而非接口层，这是关键的架构判断：
`v_*` 四张视图把 `ads_*` 与 `insight_*` 联结起来，
**后端接口只读视图、不碰明细表**。
这样 ADS 层字段调整时，只要视图定义不变，16 个 REST 接口就无需改动——
**视图因此成为数仓与服务之间的契约层**。

四张视图的分工各不相同（见第 3–4 章初稿 4.4.4 节）：
`v_zone_daily` 承担**属性补全**、`v_zone_imbalance` 承担**双路径并列**、
`v_forecast` 承担**精度透明**（把 MAPE / MAE / RMSE 与基线对比一并返回，避免只展示预测不看精度）、
`v_advice` 承担**决策闭环**（建议清单附上失衡指数与预测误差佐证）。

**而在本项目的实际交付中，这套设计被一条意外的路径强化了。**
由于 Docker 引擎在当前环境不可用，Hive 原生链路未能执行，
实际产出数据的是路径 B（`python_etl.py`）。
《实测数据附表》§〇 对此有完整的诚实声明，
并把本附表定位为**Hive 侧的期望基准值（expected value）**：

> 本附表可作为 Hive 侧的**期望基准值**（expected value），
> 待 B 岗的 Hive 环境就绪后，两者必须逐项相等——这正是严谨性的直接证据。

这一表述把"环境受限"从缺陷转成了**可验证性设计**：
报告 6.3 节的交叉验证方案正是基于这一前提设计的。

### 2.7.3 架构层面的三条工程约束

综合本章，系统的技术架构受三条可验证的约束支配：

**约束一：口径唯一。** 任何一个指标只有《02-指标定义表》一个定义来源。
该表为 M1–M12 与创新点①–④ 每个指标写明了公式、来源表、SQL 片段、对应图表与验收标准，
例如 M11 双口径电量偏差率的 SQL 直接以 JOIN 形式给出。
《03-接口规范》的字段名（如 `avgOccupancy` 是比例不是百分数、`suggestedPiles` 是新增数不是总数）
同样以契约形式固化，并由 `scripts/check-contracts.sh` 自动校验。

**约束二：一切配置外置。** 数据库地址、缓存 TTL、分区数、桩数、小时数
全部通过 `application.yml` 的 `${VAR:default}` 形式与 compose 环境变量注入。
`uev.data.region-count`、`pile-count`（23,441）、`hour-count`（4,344）
三个口径参数在 `application.yml` 第 91–93 行集中定义，
改口径只改环境变量，不动代码。

**约束三：缺一不视为通过。** `scripts/smoke_test.sh` 把关键项的缺失判为 **fail** 而非 warn：
`echarts.min.js` 缺失 → fail；`occupancy.csv` 行数异常 → fail；
`NameNode` / `DataNode` 进程未启动 → fail。
这一"严格项"与"进度项"的区分（详见 6.2.3 节）是本项目质量观的具体体现。

## 2.8 本章小结

本章从构建工具到整体架构，逐层交代了系统所用的技术及其在本项目中的具体承担。

在**集成开发环境**方面，以 Windows 11 + WSL2 为宿主、JDK 17 / Maven 3.9 / Docker 29.9.3 /
Python 3.13 为工具链，全部版本号逐条取自 `pom.xml`、`Dockerfile`、`docker-compose.yml`
与《RUNBOOK》。本节特别澄清了**后端 JDK 17 与 Hive 4.0 镜像 JDK 8 的版本差异**：
其根源是 `hive-jdbc` 3.1.3 传递依赖的 `jdk.tools:jdk.tools:1.6` 为 JDK 8 产物、
在 JDK 17 下已被移除，本项目通过把 Hive JDBC 隔离到可选 `hive` profile
并显式 exclusions 消除该冲突，使构建期与运行期彻底解耦。
容器编排由 `docker-compose.yml` 统管 **11 个服务、6 组 profile、14 个命名卷**，
profile 机制支撑了 full / app / native 三层降级启动。

在**编程语言**方面，Java 17 承担 Spring Boot 后端与三个 MapReduce 作业，
Python 3.13 承担 ETL 兜底管道与模型竞优，
二者分工的边界由计算形态划定，并通过《02-指标定义表》共享同一套公式契约。

在**Hadoop 生态**方面，逐组件说明了其在项目中承担的工序：
HDFS 承担 ODS 原始层与数仓计算层的两段存储；
MapReduce 的 `WideToLong` / `DataQualityCheck` / `PoiZoneJoin` 三个作业
分别承担宽转长、质量检查与 POI 空间连接，
其中 Map 端广播 275 个分区中心点把 1.96 亿次笛卡尔积降为 71 万次比较；
YARN 承担资源调度，其 NodeManager 2 GB / 2 vcore 的配置与 MR + Spark 共存的需求相匹配；
Flume 配置了 **12 条完全独立的采集通道**（12 source / 12 channel / 12 sink 一一对应），
并在配置头注释中固化了原版 4 个阻断级缺陷的修正记录；
Sqoop 以 `--hcatalog-table` 方式导出，并给出了 connector 版本与 TIMESTAMP 类型两个必须绕开的坑。

在**数据库技术**方面，MySQL 8.0 的 19 张表与视图承担在线服务出口，
Hive 4.0.0 的 16 张建模表承担分层加工，
两者并存的理由是**加工形态与在线服务要求的双向不可替代性**——
Hive 承担宽表 explode 与多轮迭代，MySQL 承担被预聚合到不足 5 千行的 ADS 结果的高频并发查询。

在**后端框架**方面，Spring Boot 3.2.5 + **纯 MyBatis 3.0.3** + Redis 7 的组合中，
本节指出了 `README.md` 写"MyBatis-Plus"而 `pom.xml` 声明纯 MyBatis 的口径不一致，
并明确**以 `pom.xml` 为准**，同时引用 `pom.xml` 注释中关于
`mybatis-plus-boot-starter` 在 Spring Boot 3 下会启动失败的警告。
此外说明了统一响应结构、全局异常处理的三级映射（400 / 404 / 500）
与健康检查的组件级探测与 `DEGRADED` 降级机制。

在**数据可视化技术**方面，ECharts 5 + 原生 JavaScript 的组合服务于两个具体约束：
**离线可用**（ECharts 1.03 MB 与 GeoJSON 69 KB 全部本地化，
`smoke_test.sh` 把 `echarts.min.js` 缺失判为 fail 而非 warn）
与**契约对齐**（7 个加载函数严格对应《03-接口规范》§三的映射表）。

在**整体技术架构**方面，以图 2-1 完整描述了数据源 / 接入 / 存储 / 计算 / 服务 / 展示六层结构，
并重点解释了**两条计算路径在 MySQL 视图层汇合**的设计：
汇合点刻意选在视图层而非接口层，使视图成为数仓与服务之间的契约层，
ADS 层字段调整时 16 个接口无需改动；
而在本项目的实际交付中，这条双路径设计因 Hive 链路未能执行
而被《实测数据附表》转化为一组**可验证的期望基准值**，
成为报告 6.3 节交叉验证方案的直接依据。
