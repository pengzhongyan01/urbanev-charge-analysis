# 第六章 系统测试

## 6.0 本章导读

第五章完成了从数据接入到可视化呈现的全部实现，回答了"每个功能是怎么做出来的"。
本章回答最后一个问题：**做出来的东西到底对不对、能不能用**。

测试是本系统研发流程中权重最高的一环，原因有三。
其一，本系统横跨 6 层技术栈共 11 个容器服务，
任何一层的配置错误都可能在最外层表现为"页面没数据"，
必须靠分层测试定位；其二，本系统的核心产出是**一组可被引用到规划报告中的数字**
（275 个分区、23,441 个桩、311,652,820 kWh 累计电量），
这些数字错一位，整份分析结论就失去意义；
其三，本项目采用**双计算路径**架构，
两条路径必须给出完全一致的答案，否则"口径统一"的承诺无法兑现。

本章共六节：6.1 测试方案与环境 → 6.2 接口功能测试 → 6.3 数据准确性测试（本章核心）→
6.4 性能测试 → 6.5 界面测试 → 6.6 本章小结。

测试策略按"**功能 → 准确 → 性能 → 界面**"四类组织，
对应四个递进的问题：能不能调通、数字对不对、够不够快、看得懂吗。
其中 6.3 节是本章篇幅最大、也是最有分量的一节。

> ⚠️ **本章如实记录了 5 项测试中发现并已定位的缺陷**（编号 D-01～D-05，见 6.2.4 节），
> 其中 D-01 是一处**全局异常处理器吞掉 404 语义**的设计问题，
> 会使冒烟脚本把"接口未实现"误判为"接口故障"；
> D-04 与 D-05 则是把报告附表与原始输出逐项对账时发现的两处**表述/誊写层面**的偏差
> （M6′ 的公式标注、线性回归的 RMSE），二者**均不影响任何计算结果**。
> 本章选择把它们写进来而不是藏起来——**测试报告的价值不在于"全部通过"，
> 而在于失败被准确定位、被如实记录、被修复路径明确**。

### 6.1.2 测试工具链

本项目不使用 Postman 等 GUI 工具，而是采用**四个可脚本化、可进版本库、可在答辩现场重跑**的工具。
这一选择的理由与《RUNBOOK》§1.2 "目录结构"一致：所有脚本随仓库交付，
第三方 clone 完就能跑。

**表 6-2 测试工具链清单**

| 工具 | 文件 | 检查项数 | 退出码语义 | 在测试体系中的角色 |
|---|---|---|---|---|
| 端到端冒烟测试 | `scripts/smoke_test.sh` | **7 段 / 50 个检查点** | 0 = 全通过，1 = 有失败项 | 全链路体检，一次命令验证"能否拿去答辩" |
| 契约一致性检查 | `scripts/check-contracts.sh` | 6 组 | 0 = 通过，1 = 有失败项 | 防止"文档一套、代码另一套" |
| 数据校验 | `scripts/verify_data.sh` | **36 项 SHA256 + 行数** | 0 = 通过 | 保证进入计算的数据与发布版一致 |
| Python ETL 管道 | `scripts/python_etl.py` | — | 0 = 成功 | 产出期望基准值，供 6.3 节交叉验证 |

四个工具的分工是清晰的：**`verify_data.sh` 管入口，`python_etl.py` 管计算，
`check-contracts.sh` 管契约，`smoke_test.sh` 管全局**。
`smoke_test.sh` 的头部注释把它的定位写得极为清楚：

> 这不是单元测试，是"能不能拿去答辩"的体检。
> 每次提交前跑一次，每次全链路验收跑一次。

### 6.1.3 测试策略：四类测试

**表 6-3 四类测试策略表**

| 类别 | 回答的问题 | 方法 | 本章对应节 | 通过判据 |
|---|---|---|---|---|
| **① 功能测试** | 接口能不能调通、返回结构对不对 | 逐接口 `curl` + 状态码与响应体断言 | 6.2 | `code == 200` 且字段名与契约完全一致 |
| **② 准确性测试** | 同一个指标，两条路径算出来的数一样吗 | MySQL ≡ Hive ≡ Python 三方对账 | 6.3 | 逐项数值相等（容差内） |
| **③ 性能测试** | 够不够快、缓存有没有用 | 缓存命中/未命中对照计时 + 链路耗时旁证 | 6.4 | 满足《03-接口规范》性能指标 |
| **④ 界面测试** | 用户看得懂吗、筛选联动吗、断网还能显示吗 | 6 个图表区块逐项检查 + 静态资源可达性 | 6.5 | 版式完整、交互生效、失败不白屏 |

四类测试的**优先级顺序不是随意的**。
准确性测试排在性能测试之前，是因为**性能再快、数值错了也没有意义**；
界面测试排在最后，是因为界面是数值正确之后的最后一层包装，
数值不对时界面测试没有意义。

**关于"未实现的接口报 warn 而非 fail"的设计意图。**
`[5/7]` 段的接口遍历逻辑是本脚本最精妙的一处设计：

```bash
API_LIST=$(grep -oE '(GET|POST) +/api/[a-zA-Z0-9/_{}.-]+' \
           docs/contracts/03-接口规范.md | sort -u)
for api in $API_LIST; do
  CODE=$(curl -s -o /dev/null -w "%{http_code}" "http://localhost:8080/api$api")
  if   [ "$CODE" = "200" ]; then pass "$api 返回 200"
  elif [ "$CODE" = "000" ]; then fail "$api 无响应"
  elif [ "$CODE" = "404" ] || [ "$CODE" = "501" ]; then
    warn "$api 尚未实现（$CODE）—— D 岗待补"     # ★ 进度问题，不是环境问题
  else fail "$api 返回 $CODE"; fi
done
```

这段逻辑的**设计意图非常明确**，脚本注释第 265 行写得很直白：

> 契约里定义了但 D 还没实现的接口 —— 属进度问题，不是环境问题。

也就是说：脚本要区分**"环境坏了"**与**"功能还没写"**这两类性质完全不同的问题。
前者（服务无响应）必须 `fail`，因为它意味着系统不可用；
后者（接口返回 404 / 501）只是 `warn`，因为它只意味着某个岗位的交付还没跟上，
不应该让整个团队的验收红灯。

更重要的是，脚本**不手写接口清单**，而是**从契约文件动态提取**。
脚本第 249–250 行的注释记录了这一改动的原因：

> ★ 接口清单从契约文件动态读取 —— 不再手写，避免与契约脱节
> （原手写 14 条，但契约里只有 11 条，另有 5 条是 D 待新增，数字对不上）

这实际上把契约变成了**可执行的清单**——
契约里加一个接口路径，冒烟脚本就自动多检查一个，零维护成本。

**实测结果与设计的偏差。** 在本机执行 `bash scripts/smoke_test.sh` 得到
**通过 17、警告 10、失败 13**。逐项分析这些结果与设计意图的偏差：

| 现象 | 设计预期 | 实际 | 判定 |
|---|---|---|---|
| Docker / Hive / Redis 不可用 | `warn`（环境问题） | `warn`："Docker 不可用，跳过容器检查" | **符合设计** |
| MySQL 业务表无数据 | `zone_occupancy` 无数据为 `fail`，其余为 `warn` | `✗ zone_occupancy 无数据` + 6 个 `!` 警告 | **符合设计** |
| 未实现的接口 | 应为 `warn` | 全部报 `✗ ... 无响应` | **偏差**（D-01 相关） |
| 接口清单条数 | 从契约动态提取，当前契约含 **11** 条 | 实际遍历 **11** 条 | **符合设计** |

> **表 6-7 的结论**：冒烟脚本的**分段设计与 warn/fail 分级完全按预期工作**——
> 环境不可用被正确降级为警告而非误报失败，
> 接口清单也确实从契约动态提取到了 11 条。
> 但设计意图中"未实现的接口报 warn 而非 fail"这一条**在当前实现下无法生效**，
> 原因是脚本要求未实现接口返回 404 / 501，而实际返回的是 500（缺陷 D-01）。

### 6.2.4 测试中发现的三项缺陷

**缺陷 D-01（严重）：全局异常处理器吞掉了 404 语义**

- **现象**：`GET /api/nonexistent-path` 与所有未实现的 `/api/charts/*` 接口均返回 HTTP **500**，
  响应体为 `{"code":500,"message":"系统内部错误，请查看后端日志"}`。
- **根因**：`GlobalExceptionHandler.java` 第 39–44 行的兜底处理器
  `@ExceptionHandler(Exception.class)` 会捕获 Spring 6 抛出的 `NoResourceFoundException`
  （本应映射为 404）。由于该处理器带 `@ResponseStatus(HttpStatus.INTERNAL_SERVER_ERROR)`，
  HTTP 状态码被强制改写为 500。
  实测日志中该异常出现 **23 次**，堆栈首行为
  `org.springframework.web.servlet.resource.NoResourceFoundException: No static resource api/dashboard/kpi`。
- **影响**：
  ① 语义错误——"接口未实现"被报告为"服务端内部错误"，会误导排障方向；
  ② **冒烟脚本的 warn / fail 分级设计失效**——脚本把 404 / 501 视为"进度问题"、
    把其他非 200 码视为"环境问题"，500 落入后者，导致 11 个未实现接口全部报 `fail` 而非 `warn`；
  ③ 前端收到 500 时显示"系统内部错误"而非"接口待实现"，提示不准确。
- **修复方案**：在 `GlobalExceptionHandler` 中为 `NoResourceFoundException` 增加专门的处理器，
  映射为 404 并保留 `Result.notFound(...)` 的响应结构：
  ```java
  @ExceptionHandler(NoResourceFoundException.class)
  @ResponseStatus(HttpStatus.NOT_FOUND)
  public Result<Void> handleNoResource(NoResourceFoundException e) {
      return Result.notFound("接口不存在: " + e.getResourcePath());
  }
  ```
  该改动约 6 行，不影响任何已有逻辑。
- **责任岗位**：D 岗（杨珊珊）。

**缺陷 D-02（中）：健康检查在依赖不可用时响应缓慢**

- **现象**：连续 5 次 `GET /api/health` 的 `time_total` 分别为
  1.061 / 1.024 / 1.011 / 1.022 / 1.029 秒，
  而《03-接口规范》的非功能需求为"首页聚合查询 ≤ 500 ms"。
- **根因**：`checkMysql()` 中 `dataSource.getConnection()` 在 MySQL 不可达时
  会等待 HikariCP 的连接超时（`application.yml` 第 31 行 `connection-timeout: 30000`，
  但驱动在认证阶段即失败，故实际耗时约 1 秒）。
  实测日志显示每次请求都触发一次 `UevHikariPool - Exception during pool initialization`。
- **影响**：健康检查本身耗时 1 秒，虽不影响业务接口（业务接口连不上库时同样快速失败），
  但会拖慢 `start_all.sh` 的就绪轮询与前端的 `sysStatus` 指示器刷新。
- **修复方案**：为健康检查使用独立的、连接超时更短（建议 1–2 秒）的数据源，
  或在 `checkMysql()` 中增加 `timeout` 包装，使探测失败在 500 ms 内返回。
- **责任岗位**：D 岗（杨珊珊）。

**缺陷 D-03（轻）：契约检查脚本的正则与契约写法不匹配**

- **现象**：`bash scripts/check-contracts.sh` 的第 2 组检查输出
  `! 未从契约中解析到表名`，尽管契约 04 中明确列出了 16 张表。
- **根因**：检查脚本第 88 行用 `grep -ohE 'uev_(ods|dwd|dws|ads)_[a-z0-9_]+'` 提取表名，
  而契约 04 中的表名写法是 **`uev_dwd.zone_hour_metric`**（库名与表名用**点号**分隔），
  与脚本预期的**下划线**分隔不匹配，导致一个表名也提取不到。
- **影响**：该组检查恒为警告，无法发挥作用。
  这是"检查工具自身失效"的一类问题——**它不会产生假失败，但会漏掉真问题**。
- **修复方案**：把正则改为 `uev_(ods|dwd|dws|ads)[._][a-z0-9_]+` 以兼容两种写法。
- **责任岗位**：A 岗（彭忠燕）。

**缺陷 D-04（中）：《实测数据附表》中 M6′ 的公式标注与实际计算不一致**

这是本章在数据准确性测试中发现的**一处最需要澄清的口径问题**，
它不影响任何计算结果，但会影响读者对结果的正确理解，故如实记录。

- **现象**：《实测数据附表》第一节把 M6′ 记为
  `M6′ = M6 / 充电桩数`，并给出数值 **0.1574 小时**；
  但按该公式实算，`13.1055 ÷ 23,441 = 0.000559`，
  **与附表所载的 0.1574 相差约 280 倍**。
- **根因**：附表的**数值是对的，公式的写法是不准确的**。
  `python_etl.py` 第 244 行的实际计算是
  `di = dur_p.div(pile_arr, axis=0)`，即**先按分区逐格除以该分区的桩数，再对全部单元格求均值**：
  ```
  M6′ = AVG_{z,t} [ duration_h(z,t) / charge_count(z) ]
  ```
  这与"先对所有格子求均值、再除以总桩数"是**两个不同的算子**——
  后者把大分区（446 桩）与小分区（4 桩）的时长先混在一起平均，
  再除以全市桩数，会让小分区的贡献被严重稀释。
- **实测复核**：本次测试用原始 `duration.csv`（275 列 × 4,344 行）与 `inf.csv` 独立复算，
  两种口径的结果分别为：
  | 口径 | 计算方式 | 复算结果 |
  |---|---|---|
  | 附表标注的口径 | `AVG(duration_h) ÷ 23,441` | 0.000559 |
  | **代码实际口径** | `AVG_{z,t}[duration_h(z,t) ÷ charge_count(z)]` | **0.157421** ✓ 与附表数值一致 |
  确认 **0.157421 是正确的**，等价于"全市 275 分区 × 4,344 小时共 119.46 万个单元格的 M1 均值"，
  换算为 **9.45 分钟/桩/小时**。
- **影响**：**数值无影响，表述有影响**。
  若读者按附表的字面公式复算会得到 0.000559，
  与报告、看板、KPI 卡上显示的 0.1574 对不上，
  可能被误判为"报告数据造假"或"计算有误"。
  而 0.1574 这个数在业务上是对的——
  它正是《实测数据附表》第一节所论证的"归一化后才能跨分区比较"的那个量。
- **修复方案**：把《实测数据附表》第一节 M6′ 的"契约公式"一栏由 `M6 / 充电桩数`
  改为 `AVG_{z,t}[duration_h(z,t) / charge_count(z)]`，
  并保留"= M6′ / 充电桩数"仅作为**直观类比**（而非等式），
  同时在附表该行后加一句说明"该值实为全市 119.46 万个单元格各自归一化后的均值，
  与 M6/总桩数在数学上不等"。
- **责任岗位**：A 岗（彭忠燕，附表维护人）。

**缺陷 D-05（轻）：《实测数据附表》中线性回归的 RMSE 与原始输出不一致**

- **现象**：《实测数据附表》第五节记线性回归 RMSE 为 **0.03959**，
  而其所声明的汇总来源 `data/etl_out/etl_summary.json` 中
  `"LinearRegression"` 的 RMSE 实为 **0.033266**；
  同表中基线（0.037055）与随机森林（0.032667）两项与 JSON 完全一致。
- **影响**：**不影响任何结论**，但附表自称"数据来源：etl_summary.json"，
  读者据 JSON 复核时会对不上。
  幸运的是该数值差异**不改变该表的任何结论**——
  无论取 0.033266 还是 0.03959，随机森林的 RMSE 都是三者中最小
  （0.032667 < 0.033266 < 0.037055），"树模型 RMSE 最小但 MAPE 最大"的判断依然成立。
  本报告正文统一采用 **JSON 原始值 0.033266**。
- **修复方案**：把附表第五节的线性回归 RMSE 由 0.03959 更正为 0.033266。
- **责任岗位**：A 岗（彭忠燕，附表维护人）。

> **关于 D-04 与 D-05 的一并说明。**
> 这两项都是**在测试环节把报告附表与原始数据逐项对账时**才暴露出来的，
> 且都属于"**表述/誊写层面**"而非"**计算层面**"的问题——
> 附表所载的每一个数值本身都能在原始输出中找到对应（唯一例外是线性回归 RMSE 的誊写偏差）。
> 这恰恰说明了**交叉验证机制的价值**：
> 若不做逐项对账，这两处差异会一直留在交付物中，
> 在答辩现场被追问时才暴露，其代价远高于此刻。
> 本章选择把它们写出来，正是"测试的价值不在于全部通过，而在于失败被准确记录"的直接体现。

## 6.3 数据准确性测试（本章核心）

前两节回答了"系统能不能跑"，本节回答的是本系统**最核心的问题**：
**算出来的数，到底对不对**。

《03-接口规范》第 2.2 节对数据一致性提出了明确要求：
"同一指标在 MySQL 的查询结果必须等于 Hive 直查结果"；
《02-指标定义表》则把 12 项基础指标与创新点①–④ 的公式、来源表、SQL 片段、验收标准全部固化。
本节即围绕这两份契约设计验证方案。

### 6.3.1 口径一致性验证设计

**问题的实质是"同一个指标被算了两遍，会不会算出两个数"。**

本项目的指标有两条计算路径（详见 2.7.2 节）：
**路径 A** 是 Flume → HDFS → MapReduce → Hive → Spark → Sqoop → MySQL `ads_*`；
**路径 B** 是 12 个 CSV → pandas/numpy → pymysql 直插 → MySQL `insight_*`。
两条路径由不同岗位、用不同语言、用不同引擎实现，
**如果实现中出现任何一处口径理解偏差，结论就会分叉**。

因此验证设计必须能回答三个问题：

| # | 问题 | 验证手段 | 判定标准 |
|---|---|---|---|
| Q1 | 同一指标在 MySQL 与 Hive 中的值是否相同？ | 同一 SQL 语义分别对 MySQL 直查表与 Hive 直查表执行，比对结果 | 逐项相等（浮点容差 1e-6） |
| Q2 | Python 路径的独立实现是否与 Hive 路径一致？ | 以 `python_etl.py` 输出为 Hive 侧期望基准，逐项比对 | 逐项相等（浮点容差 1e-6） |
| Q3 | 数据本身是否干净？ | 六项指标逐单元格执行 8 类质量规则 | 越界 0、重复 0、零值分布可解释 |

**验证设计的核心思想**：Q2 是**可立即执行**的——不需要集群，只需要 Python；
而它的期望值一旦确立，就成为 Q1 的 Hive 侧基准。
《实测数据附表》§〇 明确表述了这一思路：

> 本附表可作为 Hive 侧的**期望基准值**（expected value），
> 待 B 岗的 Hive 环境就绪后，两者必须逐项相等——这正是严谨性的直接证据。

### 6.3.2 Python 路径与 Hive 路径的交叉验证方案

**为什么以 `scripts/python_etl.py` 作为基准是合理的。**

这不是"退而求其次"，而是三重理由支撑的设计（详见《实测数据附表》§〇）：

1. **公式同源** —— Python 路径与 `hadoop/spark/ads_metrics.sql`、`hadoop/mr/*.java`
   使用**契约 02 中同一套指标公式**（M1–M12 与四个创新指标），不是另起炉灶重写口径。
   代码层面可验证：`python_etl.py` 第 121–122 行的注释写明
   "★ 对齐 Hive 侧 uev_dwd.zone_hour_metric 的字段：
   zone_id / hour_ts / hour_of_day / day_of_week / metric / value / is_zero"，
   字段级完全对齐。
2. **结构同构** —— 输出的 7 张 ADS 表字段与契约 04 的 `CREATE TABLE` **逐字段一致**，
   可直接被 `sqoop export` 或 `LOAD DATA` 灌入 MySQL，无需转换。
3. **可交叉验证** —— 报告 6.3 节的设计正是让 Hive 直查值与 MySQL 值对账。

**具体的交叉验证执行方案。**

```bash
# ── 步骤 1：产出期望基准（Python 侧，Hive 集群未就绪时执行）
python scripts/python_etl.py                    # 全量，181 天 / 4,344 小时
cat data/etl_out/etl_summary.json              # 汇总快照（键值对即基准值）

# ── 步骤 2：Hive 侧直查（集群就绪后由 B 岗执行）
docker exec uev-hive beeline -u 'jdbc:hive2://localhost:10000' -e "
  SELECT AVG(value) FROM uev_dwd.zone_hour_metric WHERE metric='occupancy';"

# ── 步骤 3：MySQL 侧直查
docker exec uev-mysql mysql -uroot -puev123456 uev_charge -e "
  SELECT AVG(avg_occupancy) FROM ads_zone_occupancy;"

# ── 步骤 4：三方对账（步骤 1、2、3 的结果必须相等）
```

这套方案有一个重要性质：**它可被第三方独立复现**。
`python_etl.py` 的运行不依赖 Docker、不依赖集群、不依赖网络，
只需要 129 MB 的原始 CSV 与 Python 3.13 环境——
这正好契合"第三方拿到提交包就能验证"的可复现性承诺。

**一个必须说明的口径陷阱。** 交叉验证时若直接比对
"Python 的分区均值"与"Hive 的分区均值"，两者**必然不等**——
因为 Python 侧算的是**全市总体平均**（对 1,194,600 个单元格整体求均值），
而 Hive 侧若按 `GROUP BY zone_id` 再取平均，得到的是**分区均值的均值**（275 个数的平均）。
两者相差的量级约在 1e-4，是典型的"辛普森悖论"式口径陷阱。
正确做法是**先在两侧都用同一粒度聚合，再比对**，
即比对"全市整体平均"与"全市整体平均"，
或比对"同一分区的值"与"同一分区的值"。
本节的校验表因此把**校验粒度**作为独立的一列写明。

**关于"清洗后丢弃 0 行"这一现象的正确解读。**

`python_etl.py` 第 159 行 `df["is_zero"] = (df["value"] == 0).astype("int8")`
对所有指标使用同一判定，而 duration 与 volume 在同一时段确实同时为零。

### 6.4.2 缓存命中与未命中的对照测量方法

缓存是本系统性能设计的主要手段，因此缓存的收益必须被**实测**而不是被声称。
《03-接口规范》§1.4 规定了分层 TTL 与 key 规则：

| 接口类型 | 缓存 key | TTL |
|---|---|---|
| `/dashboard/kpi` | `uev:kpi:{hash}` | 300 秒 |
| `/zones/occupancy` | `uev:zone_occ:{hash}` | 600 秒 |
| `/charts/*` | `uev:chart:{name}:{hash}` | 120 秒 |

`RedisConfig.java` 第 27 行定义 `KEY_PREFIX = "uev:"`，
与上述三类 key 的前缀完全对应，因此可用 `redis-cli` 直接定位与清理。

**具体测量步骤（待 D 岗联调后执行并回填）**：

```bash
# ── 步骤 1：测量"未命中"（清空该接口的 key 后立即请求）
redis-cli -a uev_redis_pass --scan --pattern 'uev:kpi:*' | xargs -r redis-cli -a uev_redis_pass DEL
curl -s -o /dev/null -w "未命中: %{time_total}s\n" "http://localhost:8080/api/dashboard/kpi"

# ── 步骤 2：测量"命中"（紧接着再请求一次，key 已回填）
curl -s -o /dev/null -w "命中:   %{time_total}s\n" "http://localhost:8080/api/dashboard/kpi"

# ── 步骤 3：确认缓存确实生效（查看 key 的存在与 TTL）
redis-cli -a uev_redis_pass --scan --pattern 'uev:kpi:*'
redis-cli -a uev_redis_pass TTL "uev:kpi:<hash>"

# ── 步骤 4：验证"缓存 key 含全部筛选参数"这一关键约束
#   改一个筛选参数，看 key 数量是否增加（增加 = 参数进入了 hash）
curl -s -o /dev/null "http://localhost:8080/api/dashboard/kpi?zoneId=308"
redis-cli -a uev_redis_pass --scan --pattern 'uev:kpi:*' | wc -l   # 应为 2
```

步骤 4 尤其重要：它验证的正是《03-接口规范》§1.4 加粗强调的那句话——
"缓存 key 要包含全部筛选参数（用参数哈希），否则改筛选条件会拿到旧数据，这是最常见的缓存 bug"。
**若改参数后 key 数不变，则缓存存在串味缺陷。**

> ⚠️ **本节明确标注「待回填」，不填任何编造的毫秒数。**
> 本机 Redis 未启动、MySQL 凭据不匹配，缓存路径无法真实触发；
> 在没有实测数据的情况下写入具体毫秒数，将使整份报告的可信度崩塌。
> 上述四步命令即为回填方法，回填者只需执行并把四行输出贴入本节即可。

**图 6-5 缓存命中与未命中的对照测量流程图**

```
  ┌──────────────────────────────────────────────────────────────┐
```

### 6.4.3 已实测的链路耗时（旁证）

虽然缓存对照无法实测，但有几项**真实测得**的耗时数据可作为性能侧的旁证。

**表 6-12 已实测耗时数据表**

| 环节 | 实测值 | 测量方式 | 说明 |
|---|---|---|---|
| 后端启动耗时 | **4.497 秒** | 启动日志 `Started UevChargeAnalysisApplication in 4.497 seconds` | 含 Spring 上下文初始化、Tomcat 启动、MyBatis Mapper 扫描 |
| 健康检查响应 | **1.011 – 1.061 秒** | 连续 5 次 `curl` 的 `time_total` | 因本机 MySQL 认证失败，每次触发一次 HikariCP 连接池初始化；**不代表正常环境下的耗时**，见缺陷 D-02 |
| 健康检查 TCP 连接 | **0.0006 – 0.0009 秒** | `time_connect` | 真实网络开销极小，耗时全部在依赖探测 |
| **全量 ETL 计算耗时** | **66.2 秒** | `etl_summary.json` 的 `elapsed_sec` 字段 | **覆盖 181 天 / 4,344 小时 / 6 项指标 / 1,194,600 行 × 6 的全量加工**，另含 POI 空间连接、随机森林训练、7 张 ADS 表计算 |
| 前端静态资源加载 | `index.html` **0.139 s**；`echarts.min.js` **0.004 s**；GeoJSON **0.003 s** | `curl` 的 `time_total` | 本地回环；1.03 MB 的 ECharts 仅 4 ms，本地化策略有效 |

**66.2 秒这一数字是最有力的性能旁证。**
《03-接口规范》与第三章非功能需求把"Hive 四层全链路计算"的目标定为 **≤ 30 min**，
而 Python 等价管道完成**同等规模**的全部加工仅需 **66.2 秒**——
虽然二者引擎不同（Hive/Spark 的 JVM 启动与 shuffle 开销更大），
但这个量级对比足以说明：数据规模在本项目的量级下，
**瓶颈不在计算本身，而在链路长度与数据搬运次数**。
这也解释了为什么本项目最终采用"ADS 层预聚合 + Redis 缓存"而非"查询时实时计算"的技术路线。

关于 MR 作业的规模旁证：`python_etl.py` 第 513–519 行的注释记录了一个真实的性能权衡——
"全量训练 119 万样本 × 60 棵树要 8 分钟以上，答辩现场不可接受。
这里对训练集做等间隔抽样（每 5 条取 1 条），样本量降到 ~24 万，
实测 MAPE 变化 < 0.3 个百分点，但训练时间降到 1 分钟内。"
**这条记录的意义在于它同时给出了性能数据与精度代价（< 0.3 个百分点），
是一次有据可查的权衡，而不是拍脑袋的优化。**

并论证了 duration 与 volume 零值数完全相等（均 65,365）这一强证据指向同一批深夜无活动时段、
