第三章 需求分析

3.1 需求分析目的

需求分析是软件工程中把业务诉求转化为可验证规格的关键环节。本章的目的有四：

其一，明确系统要解决的核心问题——在 275 个交通分区规模上识别充电供需的结构性错配，

并把"哪个分区、哪个时段、缺多少容量"量化出来；

其二，界定数据边界与口径边界，确认分析粒度落在分区（traffic zone）而非充电桩级，

避免出现"平均占用率很好看、但具体该建桩的地方说不清"的无效结论；

其三，识别三类使用者角色（系统管理员、运营人员、城市管理者）的差异化诉求，

并据此划定功能边界；

其四，为第四章的概要设计、第五章的详细实现与第六章的测试方案提供同一份验收基准。

3.2 系统的总体目标

本系统的总体目标是：**构建一条从原始数据到布点决策的完整数据链路，

使城市充电设施的供需失衡从"经验判断"变为"可量化、可追溯、可复现"的结论。**

围绕这一总目标，分解为八项子目标：

  • **数据可达**：以 12 个 CSV 为入口，建立从本地目录到 HDFS 的自动化增量采集通道，

使原始数据不再依赖手工拷贝。

  • **口径统一**：把 12 项基础指标（M1–M12）与 4 个创新指标的公式、来源表、

单位与边界条件固化在契约文件中，消除"同名不同义"。

  • **结构可用**：将 276 列宽表形态的原始时序数据，转换为可做多维聚合的长表，

支撑分区 × 日 × 小时粒度的分析。

  • **质量可控**：对 6 项时序指标逐项执行越界与异常判定，

清洗动作留痕、可追溯、可复核。

  • **空间可解释**：把 712,135 条 POI 落到 275 个分区上，

使充电需求的城市功能成因具备可分析的数据基础。

  • **结论可比**：设计消除分区规模差异的归一化指标，

使 4 个桩的分区与 446 个桩的分区可以在同一把尺子上比较。

  • **决策可用**：由分析结果直接生成带优先级的布点扩容建议清单，

输出为运营方与规划部门可直接采用的结论文本。

  • **系统可复现**：提供一键部署脚本、端到端体检脚本与完整运行手册，

使第三方无需原始数据也能重建 ADS 层并启动服务。

3.3 系统的可行性分析

3.3.1 技术可行性分析

（1）数据规模决定了必须使用 Hadoop 生态而非 MySQL 单机

本课题的数据规模并非"大到必须上分布式"，但其结构形态使得单机关系库难以承担：

维度具体量级对单机方案的影响
时序宽度6 张时序表均为 `time` + **275 个分区列**，共 276 列宽表无法按 `zone_id` 分组聚合，任何分析都要先转长，转换动作本身就是一次全量扫描
时序长度**4,344 个逐小时时点**（2022-09-01 ~ 2023-02-28，181 天）单表约 120 万个单元格，6 表合计约 717 万
长表化后规模275 × 4,344 × 6 ≈ **717 万行**需反复扫描才能完成多轮迭代（价格标准差 → 分区类型 → 分组聚合）
POI 空间连接**712,135** 条 POI × 275 个分区朴素笛卡尔积约 1.96 亿次距离计算，单机单线程不可接受
迭代轮次电价 σ 反推 TOU 分区 → 失衡指数 → 分区类型分组 → 预测回测每次迭代若都回读原始宽表，I/O 成倍放大

若强行用 MySQL 单机实现，只能把 275 列宽表按分区竖切成 275 张窄表，

再 UNION ALL 起来——这正是 Hive 的 LATERAL VIEW stack() 或 MapReduce 宽转长要做的事，

但 MySQL 没有原生等价物，只能靠存储过程或应用层拼装，代码量与维护成本急剧上升。

同时，712,135 条 POI 的空间连接在 MySQL 中只能靠逐行计算球面距离，

无法利用 Map 端广播分区中心点这一标准优化。

Hadoop 生态恰好覆盖了上述每一个痛点：

计算环节Hadoop 组件解决的问题
增量采集**Flume 1.11**（taildir + checkpoint）12 个 CSV 各一条独立通道，断点续传
高可靠存储**HDFS 3.3.x**原始数据与数仓分层落地，副本容错
宽转长 / 质检 / 空间连接**MapReduce 3.3.x**（`WideToLong`、`DataQualityCheck`、`PoiZoneJoin` 三个作业）动态遍历 275 列，Map 端广播分区中心点
分层建模**Hive 4.0.x**（ODS/DWD/DWS/ADS）层间职责单一、可独立追溯
多维聚合**Spark SQL 3.4**一次读入长表完成 DWS 汇总与 ADS 指标计算
库间交换**Sqoop 1.4.7**Hive ADS → MySQL 业务库

（2）关键技术点均有可验证的工程结论

宽表转长这一核心难点，本组已完成两种方案的对比实验：

使用 Hive stack() 需要硬编码全部 275 个列名，新增指标必须改 SQL 并重新编译；

使用 MapReduce 动态遍历列则可实现"新增指标零代码改动"。

该对比结论已写入《01-数据字典》与《04-数仓表结构规范》，说明关键技术路线可行且已选定。

（3）技术栈成熟度与资源门槛可控

Hadoop 3.3.6、Hive 4.0.0、Spark 3.4、Flume 1.11、Sqoop 1.4.7 均为 Apache 顶级项目的稳定版本；

后端 Spring Boot 3.2.5、前端 ECharts 5 亦为成熟选择。

部署形态为 Docker Compose 单机多容器，最低 8GB 内存 / 20GB 磁盘即可运行，

本组开发机上已完成全链路跑通记录（见 docs/RUNBOOK.md）。

3.4 系统的功能需求分析

依据第二章梳理的角色需求与可行性结论，系统功能划分为八个模块。

下表逐模块给出功能描述、输入、输出与处理逻辑。

3.4.1 数据接入与采集模块

功能描述：把分散存放的 12 个原始 CSV 通过 Flume 增量采集入 HDFS，并完成采集结果的完整性校验。

输入：12 个 CSV（6 张时序宽表 + inf / adj / distance 3 张维表 + poi + 2 张气象表）。

输出：HDFS /uev/raw/<数据集名>/ 下 12 个独立子目录，每个子目录内为按时间戳命名的分片文件。

处理逻辑：采用 Flume taildir source 监听本地目录，

12 个 CSV 各配置一条独立的 source / channel / sink 通道，避免多源写入同一目录；

channel 启用 file channel 保证断点续传，sink 写 HDFS 时保留 checksum 以便校验；

采集完成后用 hdfs dfs -ls 核对目录数与文件数，

并用 bash scripts/verify_data.sh 完成 36 项 SHA256 与行数校验。

3.4.2 数据仓库构建模块

功能描述：按 ODS–DWD–DWS–ADS 四层规范组织数据，是全系统的计算主干。

输入：HDFS 上的 12 个 CSV 原始文件。

输出：ODS 贴源宽表（每张 276 列）、DWD 长表与维表、DWS 汇总表、

ADS 应用表（一张表对应前端一张图表）。

处理逻辑：

① ODS 贴源：用 hadoop/hive/gen_ddl.py 从 CSV 表头自动生成 276 列的 DDL，

避免手写列名出错，宽表保持原貌不做任何加工；

② DWD 宽转长：运行 MapReduce 作业 WideToLong，

Mapper 动态遍历 275 个分区列，输出 zone_id / hour_ts / hour_of_day / day_of_week / metric / value / is_zero，

按 dt（yyyy-MM-dd）分区，约 717 万行；

③ DWS 轻汇总：用 Spark SQL 生成 zone_day_hour（分区 × 日 × 小时，9 字段）、

zone_day（分区 × 日，11 字段）与 zone_hour_profile（分区 × 小时画像），

并补充 zone_cluster_features 聚类特征宽表；

④ ADS 应用层：用 Spark SQL 计算 7 张核心应用表，

每张表严格对应前端的一张图表，字段与《02-指标定义表》一一对应；

创新点④ 的分区聚类结果表 zone_cluster 由 zone_clustering.sql 与

ZoneClustering.scala 另行产出。

3.4.3 数据质量检查模块

功能描述：在长表生成后对数据做系统化的质量体检，既产出清洗结果，也产出可复核的质量证据。

输入：uev_dwd.zone_hour_metric 长表、6 项指标的合法值域定义。

输出：uev_dwd.dq_zone_stat 质量画像表，字段含 valid_cnt（有效值个数）、

zero_cnt（零值个数）、outlier_cnt（越界值个数）、total_cnt（总单元格数）、

valid_rate（有效率）。

处理逻辑：执行 8 类质量规则，逐单元格判定：

占用率限定在 [0,1]、时长与电量非负、电价与服务费非负、零值单独打 is_zero 标记而不直接丢弃、

异常值按"先修复后丢弃、逐条记因"处理；

每个指标的越界阈值通过作业参数传入（如 -D uev.metric.min=0 -D uev.metric.max=1）。

关键验收口径：DWD 长表行数必须小于 ODS 对应单元格数，

二者比对是"清洗真实生效"的直接证据，也是第六章数据准确性测试的基准。

3.4.4 POI 空间连接与空间维表加工模块

功能描述：把没有分区标识的 POI 落到 275 个交通分区上，并整合出分析所需的分区综合维度表。

输入：poi.csv（712,135 条，含 primary_types 三类与 WGS84 经纬度）、

inf.csv（275 行，含分区中心点经纬度、charge_count、area、perimeter）。

输出：uev_dwd.zone_poi_count（分区 × 三类 POI 计数）、

uev_dwd.dim_zone_info（15 字段分区综合维表）。

处理逻辑：

① 空间连接由 MapReduce 作业 PoiZoneJoin 完成，

Map 端加载并广播 275 个分区中心点坐标，逐条 POI 计算球面距离并归入最近分区，

避免 712,135 × 275 的笛卡尔积；

② POI 按 primary_types 分为 lifestyle services、business and residential、

food and beverage services 三类分别计数，合计写入 poi_total；

③ 维表以 TAZID = zone_id 显式关联（inf.csv 行序与时序表列序不一致，

按行号对齐会导致全部空间分析失真且极难发现）；

④ 同一张维表内用 STDDEV_POP(e_price) > 0.05 判定是否分时电价区，

写入 is_tou_zone、price_std、price_peak、price_valley、price_gap，

供创新指标②直接消费。

3.4.5 分析指标计算模块

功能描述：在 DWS 汇总表上计算 12 项基础指标与 4 个创新指标，是分析价值的核心载体。

输入：uev_dws.zone_day_hour、uev_dws.zone_day、uev_dwd.dim_zone_info、

uev_dwd.zone_hour_metric。

输出：12 项基础指标（M1–M12）与 4 个创新指标对应的 ADS 表。

处理逻辑：基础指标覆盖需求强度（M1）、全市同期基准（M2）、

平均与峰值占用率（M3、M4）、累计电量与平均时长（M5、M6）、

日内峰谷差与波动率（M7、M8）、POI 密度与桩密度（M9、M10）、

双口径电量偏差（M11）、峰谷电价差（M12）。

四个创新指标的计算逻辑如下：

  • **创新点① 供需失衡指数**（落地表 `uev_ads.imbalance_index`）：

需求份额 D(z,t) = demand(z,t) / Σdemand，运力份额 S(z,t) = charge_count(z) / Σcharge_count，

失衡指数 I(z,t) = D(z,t) − S(z,t)。

取值范围 [−1, 1]，实际约 [−0.02, 0.02]；I > 0 表示该分区该时段的供不应求程度高于全市结构。

设计意图：消除分区规模差异（4 ~ 446 个桩），使不同规模的分区可横向比较。

  • **创新点② 分时电价弹性**（落地表 `uev_ads.price_elasticity`）：

先按电价时序标准差 σ 判定 TOU 区（σ > 0.05）与 FLAT 区，

再计算 PEAK_RATIO（17–19 时平均占用率）− VALLEY_RATIO（0–6 时平均占用率），

判读规则是 ELASTICITY 越小表示峰谷被压得越平，削峰填谷效果越好。

该分析基于观测性关联，不作因果推断。

  • **创新点③ 充电需求预测与布点扩容建议**（落地表 `uev_ads.demand_forecast`、`uev_ads.expansion_suggestion`）：

采用"同 day_of_week 同 hour_of_day 均值 × 趋势因子 γ"的统计预测方法，

前 174 天训练、后 7 天回测验证并报告 MAPE / MAE / RMSE 并与朴素基线对比；

布点规则为 建议新增桩数 = ⌈I_max(z) × charge_count(z) × 0.3⌉，

其中 0.3 为保守规划系数（一次规划不宜过大，分期建设更稳妥），优先级按 I_max 降序。

  • **创新点④ 分区聚类画像**（落地表 `uev_ads.zone_cluster`）：

以 Spark MLlib KMeans 对 275 个分区做 7 维特征聚类（k = 4），

三个必写技术点为特征标准化（否则结果被量级最大的桩密度独占）、

固定随机种子 setSeed(42) 保证可复现、用肘部法给出 k = 2~6 的 WCSS 曲线说明选 k = 4 的依据。

关键互证：紧张型簇的平均失衡指数应显著高于其他簇，

两种独立方法得到一致结论是本节最有说服力的部分。

3.4.6 在线服务与接口模块

功能描述：以 Spring Boot 提供 16 个 REST 接口，只读 MySQL 视图层，为前端与外部调用方提供数据服务。

输入：MySQL uev_charge 库的 v_* 视图与 ads_* / insight_* 明细表。

输出：统一响应结构的 JSON（code / message / data / timestamp）。

处理逻辑：

① 接口路径与出入参严格遵循《03-接口规范》，11 个核心接口（健康检查、KPI、

分区占用率、7 个图表类接口、数据字典）已固化完整示例；

② 支持 5 个公共查询参数：startDate、endDate、hourRange、zoneId、priceType；

③ Redis 缓存按接口类型分层设置 TTL（KPI 300 秒 / 分区占用率 600 秒 / 图表类 120 秒），

缓存 key 必须包含全部筛选参数的哈希，否则切换筛选条件会读到旧数据；

④ 全局异常处理器统一异常响应格式，避免堆栈信息泄露；

⑤ region-count 等配置项外置为 application.yml 中的环境相关参数；

⑥ 数据一致性保障：同一指标在 MySQL 的查询结果必须等于 Hive 直查结果。

3.4.7 可视化展示模块

功能描述：以 ECharts 5 构建深色主题的决策看板，把接口数据渲染为 6 个页面共 10 张图表。

输入：16 个 REST 接口返回的 JSON。

输出：KPI 指标卡、分区热力图 / 地图、24 小时供需曲线、失衡 TOP10 柱状图、

TOU/FLAT 双曲线、预测值与实际值对比折线图、布点建议表格、双口径电量对比图、

POI 关联散点图、分区聚类地图。

处理逻辑：前端只调用后端接口、不直接访问数据库，保证口径唯一；

四个筛选维度的变更触发所有图表联动刷新；

接口失败时显示占位提示而非白屏；

布点建议表与 KPI 概览支持 Excel / CSV 导出；

reason 字段为完整中文句子，直接展示不做二次拼装。

3.4.8 布点扩容决策建议模块

功能描述：把失衡指数与预测误差结论，转换为运营方可直接执行的扩容清单。

输入：uev_ads.imbalance_index（取分区的 I_max 与对应 hour_of_day）、

uev_ads.demand_forecast（MAPE 与回测值）、uev_dwd.dim_zone_info（charge_count）。

输出：分区级建议清单，含 zoneId、currentPiles、suggestedPiles、

priority、reason（完整中文句子）、avgOccupancy、peakGap。

处理逻辑：按 I_max 降序生成优先级（1 = 最高）；

建议新增桩数按 ⌈I_max × charge_count × 0.3⌉ 向上取整，

suggestedPiles 语义为"新增数量"而非总数，避免被误读；

reason 由模板生成完整中文句子并附上失衡指数与现有桩数，

使运营人员无需理解公式即可转成工单；

清单同时给出该分区的平均占用率与峰值缺口，供人工复核。

  • **NF-M-04 指标可扩展**：ADS 层新增指标只需新增 SQL 与表，

不影响已有模块与已有接口；

  • **NF-M-05 宽表可扩展**：宽表转长由 MapReduce 动态遍历列实现，

新增指标文件不需要改动 Java 代码；

  • **NF-M-06 文档完备**：提供数据字典、指标定义表、接口规范、数仓表结构规范四份契约

与完整运行手册，第三方可在独立环境中复现系统。

3.7.4 安全性需求

  • **NF-S-01 注入防护**：所有数据库访问使用参数化查询，杜绝 SQL 注入；
  • **NF-S-02 凭证管理**：数据库口令、缓存口令通过配置文件与环境变量注入，

不硬编码在源码中，且不随数据文件进入交付包；

  • **NF-S-03 信息泄露防护**：全局异常处理器只返回业务级错误码与提示文案，

不向前端返回异常堆栈与 SQL 片段；

  • **NF-S-04 权限控制**：系统提供 `sys_user` / `sys_role` 两张表承载账号与角色，

区分管理员、分析人员两类角色，按角色限定数据访问范围；

  • **NF-S-05 传输安全**：当前为本地 HTTP 部署，

生产化部署须引入 HTTPS 传输加密与操作审计；

  • **NF-S-06 只读优先**：16 个对外接口全部为查询接口，无写操作，

从接口层面缩小攻击面。

结论：四类非功能需求共 22 条（性能 6 / 可靠性 6 / 可维护性 6 / 安全性 6），

4.3.1 数据接入模块的概要设计

输入输出：

项内容
输入`data/raw/` 下 12 个 CSV（6 张时序宽表 + `inf` / `adj` / `distance` / `poi` + 2 张气象表）

① 环境探测：find_data.sh 按 UEV_DATA_DIR → data/raw/ → ../数据/UrbanEV/ 顺序自动定位数据目录

       ↓
④ 采集校验：hdfs dfs -ls 核对 12 个子目录与分片数，
   hdfs dfs -cat 抽查首行表头是否为 time + 275 个分区列

⑤ 输出采集结论（目录数 / 分片数 / 校验状态），供 M2 消费

与其他模块的接口：

4.3.2 数据仓库模块的概要设计

模块描述：本模块是系统的计算主干，承担从原始宽表到可用分析结果的全部加工工作。

输入输出：

项内容
输入M1 产出的 HDFS 分片文件（12 个子目录）
输出ODS 贴源表（脚本自动生成 DDL）+ DWD 4 张 + DWS 4 张 + ADS 8 张加工层表
关键约束分区键统一为 `dt`（`yyyy-MM-dd`）；长表化后行数约 275 × 4,344 × 6 ≈ 717 万行

处理流程：

① ODS 贴源：python3 hadoop/hive/gen_ddl.py 从 CSV 表头自动生成 276 列 DDL
   → hdfs dfs -put → beeline -f 建表 → LOAD DATA INPATH 装载
   ⚠️ LOAD DATA INPATH 是移动不是复制，须先 put 到临时目录再装载
       ↓
② DWD 宽转长：hadoop jar uev-mr.jar com.uev.mr.WideToLong
   /uev/raw/occupancy/ → /uev/dwd/long/occupancy
   -D uev.metric.name=occupancy
   → Mapper 动态遍历 275 列 → (zone_id, hour_ts, hour_of_day, day_of_week, metric, value, is_zero)
   ⚠️ 6 个指标各执行一次，输入目录与 uev.metric.name 同时改
       ↓
③ DWD 质量检查：hadoop jar uev-mr.jar com.uev.mr.DataQualityCheck
   -D uev.metric.min=0 -D uev.metric.max=1
   → 产出 dq_zone_stat（valid_cnt / zero_cnt / outlier_cnt / total_cnt / valid_rate）
   ⚠️ 验收口径：DWD 行数 < ODS 单元格数，证明清洗真实生效
       ↓
④ 空间连接与维表：hadoop jar uev-mr.jar com.uev.mr.PoiZoneJoin
   /uev/raw/poi/ → /uev/dwd/zone_poi_count -D uev.zone.info.path=/uev/raw/inf/
   → Map 端广播 275 个分区中心点，Haversine 距离归入最近分区
   → Spark SQL 整合出 dim_zone_info（15 字段，含 is_tou_zone / price_std / price_gap）
       ↓
⑤ DWS 汇总：spark-sql --master local[*] -f ads_metrics.sql
   → zone_day_hour（分区×日×小时）/ zone_day（分区×日）/ zone_hour_profile（分区×小时）
   → zone_cluster_features（7 维聚类特征宽表）
       ↓
⑥ ADS 产出：同一份 SQL 继续计算 7 张 ADS 表（dashboard_kpi / zone_occupancy /
   hourly_supply_demand / imbalance_index / price_elasticity / demand_forecast /
   expansion_suggestion），并由 zone_clustering.sql + ZoneClustering.scala 产出 zone_cluster
       ↓
⑦ 导出 MySQL：sqoop export --hcatalog-table uev_ads.xxx --hcatalog-database uev_ads -m 1
   ⚠️ Hive TIMESTAMP → MySQL 用 VARCHAR(30) 接收；connector 需 8.x 否则连 MySQL 8 报 query_cache_size

与其他模块的接口：

向上（对 M1）以 HDFS 路径 + Flume 通道命名 为接口；

向下（对 M3）以 《04-数仓表结构规范》中的表名与字段名 为接口——

M3 的所有 SQL 直接引用 uev_dws.zone_day_hour、uev_dwd.dim_zone_info 等表，

不复制粘贴数据，避免口径漂移；

横向（对 M5）以 建表 9 步检查清单 为接口，每一步都有明确的验收命令与期望输出。

4.3.3 指标分析模块的概要设计

模块描述：把数仓中的明细与汇总，转化为可解读、可比较、可决策的指标与结论。

输入输出：

项内容
输入`uev_dws.zone_day_hour`、`uev_dws.zone_day`、`uev_dwd.dim_zone_info`、`uev_dwd.zone_hour_metric`
输出12 项基础指标 + 4 个创新指标；ADS 层 8 张表；`insight_*` 5 张洞察表
关键约束两条路径并行——E 组用 pandas 直接从 CSV 复算并以 pymysql 直插 `insight_*`，不被 M2 的 Sqoop 排期卡住

处理流程：

① 基础指标层（M1–M12）
   需求强度 M1 = duration_h / charge_count      全市同期基准 M2 = Σduration / Σcharge_count
   平均占用率 M3 / 峰值占用率 M4                 累计电量 M5 / 平均时长 M6
   日内峰谷差 M7 = MAX(occ) − MIN(occ)           占用率波动率 M8 = STDDEV_POP(occ)
   POI 密度 M9 / 桩密度 M10                      双口径电量偏差 M11 / 峰谷电价差 M12
       ↓
② 创新点① 供需失衡指数
   D(z,t) = demand(z,t) / Σ demand    S(z,t) = charge_count(z) / Σ charge_count
   I(z,t) = D(z,t) − S(z,t)   → uev_ads.imbalance_index（正负值均须出现）
       ↓
③ 创新点② 分时电价弹性
   σ_price(z) = STDDEV_POP(e_price) > 0.05 → TOU 区，否则 FLAT 区
   ELASTICITY = AVG(occ | 17≤h≤19) − AVG(occ | 0≤h≤6)   → 值越小，削峰效果越好
   ⚠️ 结论只写观测性关联，不作因果推断
       ↓
④ 创新点③ 需求预测与布点建议
   基础值 = AVG(volume | 同 day_of_week 同 hour_of_day)   γ = AVG(近7天) / AVG(全期)
   predict = 基础值 × γ
   回测：前 174 天训练（2022-09-01~2023-02-21），后 7 天验证（02-22~02-28），报告 MAPE/MAE/RMSE
   建议新增桩数 = ⌈I_max(z) × charge_count(z) × 0.3⌉，优先级按 I_max 降序（1 = 最高）
       ↓
⑤ 创新点④ 分区聚类画像
   特征向量 X(z) = [avg_occupancy, peak_valley_gap, occupancy_std, avg_duration,
                    poi_density, pile_density, price_std]   （7 维）
   标准化 → setSeed(42) → 肘部法在 k=2~6 中选出 k=4 → KMeans → uev_ads.zone_cluster
   互证：紧张型簇的平均失衡指数应显著高于其他簇
       ↓
⑥ 结论落表：Hive ADS（供 B 走 Sqoop）+ MySQL insight_*（E 直插），两路口径按同一份
   《02-指标定义表》对齐，并在报告 6.3 节做 MySQL vs Hive 一致性校验

与其他模块的接口：

向上（对 M2）以 表名与字段名 为接口，只读不写数仓；

向下（对 M4）以 ADS 表 + insight_* 表 为接口，

其中 ADS 表供 ads_* 落地、insight_* 供视图联查，两者在视图层汇合；

横向（对 M5）以 验收标准 为接口——

《02-指标定义表》为每个创新指标写明验收口径（如"TOP10 应包含 CBD 类分区"），

冒烟测试按此逐条核对。

4.3.4 服务与可视化模块的概要设计

模块描述：把 M3 的结论以标准化接口与可视化看板的形式交付给三类使用者。

输入输出：

项内容
输入MySQL `uev_charge` 的 4 张视图 `v_zone_daily` / `v_zone_imbalance` / `v_forecast` / `v_advice`
输出16 个 REST 接口的 JSON 响应；看板 6 页 10 图；Excel / CSV 导出文件

处理流程：

① 请求进入：Spring Boot Controller 接收 GET 请求，统一前缀 /api

       ↓
② 参数校验：5 个公共可选参数 startDate / endDate / hourRange / zoneId / priceType

       ↓
③ 缓存判定：以全部筛选参数的哈希构造 key
   key = uev:{类型}:{name}:{hash}
   ├── 命中 → 直接返回缓存结果（TTL：KPI 300s / 分区占用率 600s / 图表 120s）
   └── 未命中 → 查 MySQL 视图 → 回填缓存 → 返回

4.4 数据库设计

4.4.1 E-R 图设计说明

本系统的数据分为三类实体：

（1）分区维表实体（Zone Dimension）

对应 uev_dwd.dim_zone_info，是全系统的核心维度实体，

一条记录代表深圳 275 个交通分区之一。

主键为 zone_id（= inf.csv 的 TAZID）。

该实体承载两类属性：

静态属性（longitude、latitude、charge_count、area、perimeter）

与派生的空间属性（poi_lifestyle、poi_business、poi_food、poi_total）

以及价格属性（is_tou_zone、price_std、price_peak、price_valley、price_gap）。

（2）指标事实表实体（Metric Fact）

对应 uev_dwd.zone_hour_metric（最细粒度）与其上游的

uev_dws.zone_day_hour、uev_dws.zone_day、uev_ads.* 系列。

一条记录代表"某个分区在某个时间点的某个指标取值"。

该实体的度量属性为 value（DOUBLE），维度属性为

zone_id、hour_ts、hour_of_day、day_of_week、metric，

另有 is_zero 标记原值是否为零（疑似缺失）。

（3）系统实体（System Entity）

对应 MySQL 侧的 sys_user（用户）、sys_role（角色）、sys_operation_log（操作日志）

与 sys_data_dictionary（数据字典），

用于承载应用自身的账号、权限与审计信息，与分析数据分离存放。

（4）并行写入与视图汇合的设计说明：

这是本系统在数据架构上最关键的一个决定，理由有三：

  • **解耦时间依赖**——E 组的交付节点早于 B 组的 Sqoop 导出节点，

若强制 E 走 Hive → Sqoop 链路会产生时间倒挂；改为直插后两条路径完全并行。

  • **不牺牲核心创新点的可控性**——创新点④的聚类本就要写自己的 Spark MLlib 代码，

塞进 B 的 Spark 脚本等于把核心工作交给他人执行。

  • **口径一致性仍可保障**——两条路径都以《02-指标定义表》为唯一公式来源，

并在报告 6.3 节做"同一指标 MySQL 查询值 = Hive 直查值"的逐项校验，

不一致时先改契约再改实现并登记 CHANGELOG。

汇合点被刻意放在视图层：

v_* 把 ads_* 与 insight_* 联结起来，

后端接口只读视图、不碰明细表。

这样 ADS 层字段调整时，只要视图定义不变，16 个 REST 接口就无需改动——

视图因此成为数仓与服务之间的契约层。

第七章 总结与展望

7.1 总结

本课题以 UrbanEV 开源数据集（CC0 1.0）为对象，完成了一套"从原始数据到布点决策"的

完整城市充电桩数据分析系统。从数据接入、数仓建模、指标计算、后端服务到可视化呈现，

系统打通了全链路，并在四个分析维度上给出了具有业务解释力的量化结论。

以下从六个层面归纳本课题的成果。

7.1.1 数据接入与治理

本课题完成了 12 个 CSV（129MB 级）的自动化接入与规范化治理。

接入环节基于 Flume taildir 增量采集，**为 12 个 CSV 各自配置了一条独立的

source / channel / sink 通道**，落到 HDFS 的 12 个独立子目录，与 Hive 建表脚本一一对应；

这一修正避免了多源写入同一目录导致的建表错配。

数据治理环节在 MapReduce 层实现了三类作业：

WideToLong 将 time + 275 个分区列的宽表（276 列）转为标准长表

（zone_id / hour_ts / hour_of_day / day_of_week / metric / value / is_zero），

长表化后约 717 万行；DataQualityCheck 以 8 类规则逐单元格判定，

产出 dq_zone_stat 质量画像表（有效数、零值数、越界数、有效率），

实现"先修复后丢弃、逐条记因"；PoiZoneJoin 把 712,135 条 POI

按 Map 端广播的 275 个分区中心点完成最近邻空间连接。

数据完整性的验证形成了可复核的证据链：

采集后执行 36 项 SHA256 与行数校验，计算后以 DWD 行数小于 ODS 对应单元格数

作为"清洗真实生效"的硬性判据。此外，针对实测发现的 9 个坑

（数据是宽表而非长表、inf.csv 行序与时序表列序不一致、TAZID 为字符串、

三套时间格式并存、无分时电价标识字段等），

逐条在《01-数据字典》v1.0 中登记了现象、原因与处理方式，

使后续开发不再重复踩坑。

7.1.2 数仓建模

本课题建成 ODS–DWD–DWS–ADS 四层数仓，16 张 Hive 建模表各司其职：

ODS 贴源层保持 CSV 原貌不作任何加工，275 列宽表由 gen_ddl.py 从 CSV 表头自动生成 DDL，

杜绝手写 275 个字段名的出错风险；

DWD 层完成宽转长、清洗与维度补齐，

其中 dim_zone_info 一张表就把分区静态属性（经纬度、桩数、面积、周长）、

空间属性（三类 POI 计数与总数）与价格属性（是否分时电价、电价标准差、峰谷价差）

整合在一起，成为创新点②的直接入口；

DWS 层提供分区 × 日 × 小时、分区 × 日、分区 × 小时画像三类汇总粒度，

以及 7 维聚类特征宽表；

ADS 层 8 张表严格遵循"一张表 = 前端一张图表"的原则，字段与《02-指标定义表》一一对应。

建模过程中最具工程价值的一点是宽表转长的方案选型：

Hive stack() 需硬编码 275 个列名、新增指标必须改 SQL 并重新编译，

而 MapReduce 动态遍历列可实现"新增指标零代码改动"，

最终确定并实现了后者。该决策不仅解决了可维护性问题，

也使"熟练掌握 Hadoop"从口号变成了可验证的代码证据。

分层规范通过《04-数仓表结构规范》固化，并配套"建表 9 步检查清单"，

每一步都有明确的验收命令与期望输出。

7.1.3 分析方法与创新指标

本课题的核心贡献在于 4 个创新指标的设计与实现。

创新点① 供需失衡指数（I(z,t) = D(z,t) − S(z,t)）直面"分区规模差异导致绝对量不可比"这一根本问题：

福田桩多、坪山桩少，直接比占用率或电量必然误判，

而把需求与运力同时归一化为"占全市同期的份额"再取差值，

使 4 个桩的分区与 446 个桩的分区可以放在同一把尺子上比较，

取值范围 [−1, 1]，正值即供不应求。

创新点② 分时电价弹性利用数据集同时提供"分区级价格时序"与"分区级占用率时序"这一独有优势，

先用电价时序标准差 σ 反推哪些区实行分时电价（TOU 区）、

哪些区执行固定电价（FLAT 区），再比较两组在 17–19 时与 0–6 时的占用率差，

把"分时电价到底有没有真的削峰填谷"这一长期停留在概念层面的问题，

变成了可测量的数字（判读规则为 ELASTICITY 越小、峰谷压得越平、削峰效果越好）。

创新点③ 需求预测与布点扩容建议采用"同 day_of_week 同 hour_of_day 均值 × 趋势因子"

的统计预测方法，

以前 174 天训练、后 7 天回测并报告 MAPE / MAE / RMSE 并与朴素基线对比，

再由分区峰值失衡指数按 ⌈I_max × charge_count × 0.3⌉ 生成带优先级的扩容建议，

并输出可直接进工单的完整中文句子。

创新点④ 分区聚类画像用 Spark MLlib KMeans 对 275 个分区做 7 维特征聚类（k = 4），

刻意处理了三个技术要点：特征标准化（否则结果被量级最大的桩密度独占）、

固定随机种子 setSeed(42)（保证可复现）、肘部法给出 k = 2~6 的 WCSS 曲线说明选 k = 4 的依据；

更关键的是用"紧张型簇的平均失衡指数应显著高于其他簇"完成了两条独立方法的交叉互证。

四个指标共同把"哪里缺桩"推进到"哪个分区、哪个时段、缺多少、按什么优先级补"；

其中分时电价弹性以峰谷差这一可测量量，把"电价引导削峰"从概念变成数字。

7.1.4 后端服务与接口

本课题实现了基于 Spring Boot 3.2.5 的后端服务，对外提供 16 个 REST 接口，

统一采用 {code, message, data, timestamp} 响应结构，

11 个核心接口（健康检查、KPI 概览、分区占用率、7 个图表类接口、数据字典）

的完整出入参已在《03-接口规范》中固化，前端可直接按规范开发。

接口层的三个设计决策体现了工程判断：

其一，缓存 key 必须包含全部筛选参数的哈希，

这是最容易被忽略却最常引发"改了筛选条件却拿到旧数据"的坑，

本系统按接口类型分层设置 TTL（KPI 300 秒 / 分区占用率 600 秒 / 图表类 120 秒）；

其二，接口只读视图、不直接访问明细表，

ads_* 与 insight_* 两条并行写入路径在 v_* 视图层汇合，

视图因此成为数仓与服务之间的契约层，ADS 字段调整时接口无需改动；

其三，两条计算路径的口径一致性由机器校验保证——

同一指标在 MySQL 的查询结果必须等于 Hive 直查结果，

不一致时先改契约再改实现并登记 CHANGELOG，把"口径一致性"从人工约定变成了可执行的检查项。

服务层同时提供了全局异常处理、参数校验、JWT 角色鉴权与操作日志，

并通过 /api/health 暴露 mysql / redis 组件状态与分区总数（配置为 275），

使系统状态可被外部观测。

7.1.5 可视化呈现

本课题以 ECharts 5 构建了深色主题的决策看板，6 个页面共 10 张图表，

覆盖 KPI 指标卡、分区热力图与深圳分区地图、24 小时供需曲线、

失衡指数 TOP10 横向柱状图、TOU / FLAT 双曲线对比图、

预测值与实际值对比折线图、布点扩容建议表格、双口径电量偏差对比图、

POI 关联分析与分区聚类地图。

展示层的关键在于"可解释"而非"好看"：

失衡 TOP10 的 tooltip 同时给出需求份额与运力份额两个分量，

使读者能自行验证 I = D − S 的计算过程；

电价弹性图在标题旁并列展示 TOU 与 FLAT 两组的 ELASTICITY，

答辩时可直接读出结论；

预测曲线把预测值与实际值画在一起并附 MAPE，不做"只展示预测不看精度"的选择；

布点建议表的 reason 字段是完整中文句子，含失衡指数与现有桩数，

运营人员无需理解公式即可转为工单；

suggestedPiles 严格定义为"新增数量"而非总数，避免被误读。

系统还支持 Excel / CSV 导出，结论可直接进入汇报材料。

ECharts 与深圳分区 GeoJSON 均已本地化存放，不依赖 CDN，答辩现场无外网也能正常渲染。

7.1.6 工程化与可复现性

本课题在工程化方面着力甚多，这既是课程要求，也是本系统区别于一般作业的关键特征。

契约驱动的协作机制是其中最具特色的一项：

四份契约文件（数据字典、指标定义表、接口规范、数仓表结构规范）被确立为全组唯一事实源，

任何口径变更必须先改契约、登记 CHANGELOG、再由下游拉取生效，

scripts/check-contracts.sh 自动扫描"契约定义 ↔ 建表脚本 ↔ Controller ↔ 计算脚本"四处一致性，

检查不过不能合并——这把"指标定义"从口头约定变成了可校验的工程产物。

端到端可复现是另一项硬指标：

Docker Compose 提供一键编排，start_all.sh 自动探测环境并在

full / app / native 三种模式间降级选择；

smoke_test.sh 分 6 组完成数据文件、Hive 四层表、MySQL 业务表、后端接口、

Redis 缓存与契约一致性的端到端体检；

《RUNBOOK》以"拿到文档的人 30 分钟内跑起系统"为编写目标；

交付包包含全部建表 DDL、每张 MySQL 表的前 100 行样例 CSV

以及 export_to_mysql.sh / restore_from_mysql.sh / rebuild_ads.sh 三个脚本，

使第三方无需下载 129MB 原始数据即可重建 ADS 层并启动服务。

129MB 的原始数据不进 Git（避免仓库膨胀与 clone 不可用），

而由 download_data.sh 可再生，这一取舍使"可复现"与"可分发"同时成立。

7.2 不足与改进方向

本系统在方法与工程上取得了上述成果，但受数据范围、模型能力与工程形态的客观限制，

仍存在若干明确的不足。本节逐条给出"现象 → 原因 → 改进设想"。

7.2.1 数据覆盖范围单一

现象：全部分析建立在深圳单一城市、2022-09-01 至 2023-02-28 共 181 天的数据上，

时间跨度不足半年且不含完整的季节周期；结论无法直接外推到其他城市或其他季节。

原因：UrbanEV 数据集本身只提供深圳一个城市、6 个月时长的数据，

公开的高粒度充电桩运行数据稀缺，可选数据源有限；

同时系统未引入任何模拟或合成数据，以保证结论完全来自真实运营记录。

改进设想：一方面可在现有框架上接入第二个城市的数据集做横向对照，

验证失衡指数与聚类画像在不同城市的适用性；

另一方面可把气象数据（数据集已含宝安机场与福田两个气象站的逐小时气温、气压、湿度、降水）

真正接入预测模型，检验季节与天气因素对需求的解释力；

若需扩展时间跨度，可通过 Flume 增量采集机制持续接入后续月份的同源数据，

本系统的采集链路无需改造。

7.2.2 未考虑充电桩故障率与设备异质性

现象：全部供给侧指标以 charge_count（分区充电桩总数）表示，

隐含假设是"所有充电桩在同一时刻均可服务"；

不同功率等级、不同服务能力的充电桩被视为同质。

原因：UrbanEV 数据集提供的是分区级聚合指标，没有桩级的在线状态与设备档案，

无法识别故障、离线或被占用但不可用的桩；

且数据本身以"分区级"而非"桩级"为粒度（这一点在《01-数据字典》中已明确警示）。

改进设想：若能获得桩级状态数据，应把供给侧口径从"名义桩数"改为"有效可服务桩数"，

即 charge_count × (1 − 故障率)，并对失效桩按 is_zero 等信号识别；

更完整的方向是引入桩级画像，把分区级供给拆解为"快充桩数 / 慢充桩数 / 故障桩数"，

使失衡指数能进一步区分"总量不足"与"结构错配"两种截然不同的成因。

7.2.3 未考虑用户行为异质性

现象：需求侧建模以分区聚合量为单位，

把同一分区内所有用户的到离时间、车型、充电偏好视为同质。

原因：数据集只提供分区级的占用率、时长与电量时序，

不含任何用户标识、订单明细、车辆类型或停留时间分布；

在现有口径下，个体行为差异在聚合过程中被完全抹平。

改进设想：可从"分布特征"而非"个体"入手——

例如比较不同分区内充电时长的分布形态（而不只是均值 M6），

用时长分布的长尾程度区分"少数长时占用"与"大量短时周转"两类完全不同的供给问题，

前者对应大功率桩不足、后者对应周转效率低下，两者的扩容策略截然不同；

若后续能获得订单级数据，则应引入用户聚类与出行链建模，

把"分区需求"细化为"通勤型 / 目的地型 / 过路型"三类，并据此给出差异化建议。

7.2.4 预测模型未纳入天气与节假日等因素

现象：创新点③的预测公式为"同周期均值 × 趋势因子"，

仅利用了 day_of_week 与 hour_of_day 两个周期性维度，

未纳入气温、降水与法定节假日等已知会显著影响充电行为的因素。

原因：一是气象数据只覆盖两个站点、需要做"分区到最近气象站"的映射，

在课题时间窗内优先级低于核心指标；

二是节假日需要额外接入权威节假日日历数据源，

而本课题为控制数据来源的合规性与可复现性，坚持只使用 CC0 协议的数据集；

三是统计预测方法在分区级周同环比上已达可用精度，

在时间有限的情况下优先保证了主线的完整与可演示性。

改进设想：引入气象与节假日因子后，可将预测模型从"同周期均值"

升级为带外生变量的回归形式 predict = f(基础值, γ, 气温, 降水, 节假日哑变量)，

并通过回测比较引入前后的 MAPE 改善幅度；

同时应保留朴素基线作为对照，防止引入变量后模型反而过拟合。

7.2.5 聚类结果未做稳定性检验

现象：创新点④的 KMeans 结果通过"固定种子 + 肘部法"保证了可复现，

但未对聚类结果本身的稳定性做检验，即没有回答"换一个随机种子，簇的划分会不会明显改变"。

原因：KMeans 属于局部最优算法，不同初始中心可能导致不同的簇划分；

本课题以"可复现"为主要目标，通过 setSeed(42) 消除了随机性，

但稳定性（对初始化的不敏感度）是另一个维度的性质，两者不能互相替代；

同时该创新点在契约中被标注为"可选增量"，实现时间被压缩。

改进设想：应补充两项检验——

其一，多次随机初始化的一致性检验（如 20 次不同种子下的簇分配，

用调整兰德指数 ARI 衡量两次划分的相似度，ARI 稳定在高位才说明簇结构稳健）；

其二，自助法稳定性检验（对 275 个分区做有放回重采样，

统计每个分区的簇归属在重采样中的一致率）。

此外应报告各簇的规模分布，若出现"某簇仅含 1~2 个分区"的极端情况，

说明 k = 4 的选择需要重新论证。

7.2.6 实时性依赖离线批处理

现象：系统当前为纯离线批处理架构，数据从采集到看板更新存在一个完整的批处理周期，

无法支撑"刚刚发生的拥堵"这类实时调度需求。

原因：本课题的核心价值在于分区级的结构分析，

小时级批处理已能满足分析需求；

且实时化会引入流处理组件（Kafka / Flink）的额外运维成本，

与"30 分钟可复现"的交付目标存在张力；

此外数据集本身是历史静态数据，实时化在当前数据条件下没有实际意义。

改进设想：若数据源替换为实时充电站心跳数据，

可复用现有的 Flume 采集通道，将 WideToLong 与 DataQualityCheck 改造为流式作业，

在 ADS 之上增加一层实时中间表，用毫秒级更新替代批处理；

Kafka + Flink 是自然的技术选型，本课题已实现的 Flume 通道化设计恰好为其预留了接入点。

7.2.7 缺少用户画像与支付链路数据

现象：系统的输出止于"分区层面的建议"，无法回答

"这个分区的充电用户是谁、他们为什么在这里充电、一次充电实际花了多少钱"这类问题，

也无法评估分时电价对用户侧支出的实际影响。

原因：UrbanEV 数据集只提供分区级的运行指标，

不含用户身份、订单、支付与结算数据；

《01-数据字典》已明确 e_price.csv 与 s_price.csv 只是分区级的价格时序，

不含实际成交价与优惠信息。

改进设想：若能接入订单级数据，可做两件事：

其一，构建充电用户画像（通勤 / 居住 / 目的地 / 过路四类），

使扩容建议从"分区缺桩"细化到"为哪类用户、在什么时段、缺什么样的桩"；

其二，把分时电价引导效果从"占用率曲线的观测性关联"

推进到"用户侧实际支出的变化"，实现从运营侧视角到用户侧视角的跨越，

这也能实质性缓解本系统当前"不做因果推断"的学术严谨性限制。

7.2.8 双路径一致性依赖人工校验

现象：B 的离线数仓通道与 E 的探索性分析通道并行计算同一批指标，

二者的一致性目前依靠报告 6.3 节的人工对照测试保证，

尚未实现自动化的持续校验。

原因：两条路径的定位不同——B 承担生产化的 ETL 管道，

E 承担快速验证与创新点探索，二者的运行环境与触发时机本就不同；

设计一条自动化的一致性校验流水线需要额外的调度与告警设施，

在课程作业的时间窗内优先级靠后。

改进设想：应把"同一指标双路比对"做成常态化检查项——

在 CI 或定时任务中执行一组固定的比对 SQL，

逐指标比较两路结果的差值是否落在容差内，

超出阈值即告警并生成差异明细；

该检查可直接复用《03-接口规范》与《04-数仓表结构规范》已固化的表名与字段名，

实现成本不高而收益明确。

7.2.9 布点建议中的 0.3 系数缺乏实证支撑

现象：布点建议规则中的保守规划系数 0.3 是基于工程经验的业务判断，

未经数据验证，不同分区也未做差异化处理。

原因：该系数反映的是"一次规划不宜过大、分期建设更稳妥"的运营常识，

而非从数据中推导出的最优值；

在缺少桩级建成成本、场租成本与实际收益数据的条件下，

任何系数都无法被实证优化。

改进设想：至少应做敏感性分析——

把系数在 0.1 ~ 0.5 区间内取值，

观察建议清单的排序稳定性与总建议桩数的变化，

若 TOP10 分区排序在区间内保持不变，说明结论对系数不敏感、建议稳健；

若排序剧烈变动，则说明当前建议过度依赖于一个人为参数，必须在报告中明确提示。

更深一步的做法是引入投资回报视角，

用"每新增一桩的边际收益"作为排序依据，使优先级从经验规则升级为量化规则。

7.3 展望

基于上述不足与改进设想，本课题的后续工作可从以下五个方向推进。

方向一：扩展数据源，向多城市与长周期演进。

当前的深圳单城市、181 天数据限制了结论的外推能力。

后续可引入第二个城市的数据集做横向对照，

验证失衡指数、聚类画像在不同城市结构下的稳定性，

并通过 Flume 增量采集持续接入同源的增量数据，

把时间跨度扩展到覆盖完整季节周期，

使"季节性供需错配"成为可分析的主题。

方向二：引入外生变量与更丰富的模型族。

把已有的两个气象站通过"分区到最近气象站"的映射接入分区维度，

叠加官方节假日日历，

将预测模型从"同周期均值 × 趋势因子"升级为含外生变量的回归或梯度提升模型，

并引入 LSTM / Transformer 等序列模型做对照实验；

选型标准应从"能否跑起来"转为"回测精度 + 现场可复现性"的综合权衡。

方向三：从供给总量分析走向供需结构分析。

在引入桩级档案与故障率数据后，

把供给侧口径从名义桩数改为有效可服务桩数，

把快充、慢充、故障桩分离统计；

同时引入用户聚类画像，区分通勤型、目的地型与过路型充电需求，

使建议从"这个分区缺 N 个桩"细化为"这个分区在晚高峰需要 N 个快充桩，

主要服务通勤用户"。

方向四：增强结论的因果性与决策闭环。

当前的电价弹性结论基于观测性关联，本质上无法排除"分区功能类型差异"这一混杂因素。

后续可尝试双重差分或倾向得分匹配等准实验方法，

在存在政策实施前后对照样本时，尝试给出更接近因果的估计；

同时把建议清单接入实际建设与运营反馈，形成"建议—实施—复盘"的闭环，

用真实反馈校准 0.3 这一经验系数。

方向五：推进实时化与工程产品化。

在数据源具备实时条件的前提下，

将 Flume + MapReduce 链路改造为 Kafka + Flink 的流式管道，

在 ADS 之上增加实时中间表，把看板从批处理更新改为准实时更新；

同时引入自动化的一致性校验流水线与持续集成，

把当前依赖人工执行的契约一致性检查与双路指标比对全部自动化，

使系统在规模扩大后仍能保持质量不衰减。

7.4 本章小结

本章从六个层面归纳了全文成果：

数据接入与治理方面，建成 12 条 Flume 独立采集通道与三个 MapReduce 作业，

把 276 列宽表治理为约 717 万行标准长表，

并以 8 类质量规则与"DWD 行数小于 ODS"的硬性判据留下可复核的清洗证据；

数仓建模方面，建成 ODS–DWD–DWS–ADS 四层数仓与 16 张 Hive 建模表，

解决了宽表转长这一核心技术难点并给出方案选型依据；

分析方法方面，设计的 4 个创新指标——

供需失衡指数、分时电价弹性、需求预测与布点建议、分区聚类画像——

把"哪里缺桩"推进到"哪个分区、哪个时段、缺多少、按什么优先级补"；

后端服务方面，16 个 REST 接口配合分层缓存与只读视图的解耦设计，

把两条并行计算路径在视图层汇合并以机器校验保证口径一致；

可视化方面，以 6 页 10 图把结论渲染为可直接决策的看板；

工程化方面，契约驱动机制与一键复现交付使第三方无需原始数据即可重建系统。

同时本章坦率指出了 9 条不足，

覆盖数据覆盖范围单一、充电桩故障率与用户行为异质性缺失、

预测模型未纳入天气与节假日、聚类结果未做稳定性检验、

实时性依赖离线批处理、缺少用户画像与支付链路数据、

双路径一致性依赖人工校验、经验系数缺乏实证支撑等方面，

并逐条给出了可执行的改进设想。

展望部分提出五个方向：数据源向多城市与长周期演进、

模型引入外生变量与更丰富的模型族、

分析从供给总量走向供需结构、

结论从观测性关联走向准因果推断、

系统从批处理走向实时化与工程产品化。

这些方向既是对本课题现有成果的自然延伸，

也为后续学习与研究提供了清晰的问题清单。
