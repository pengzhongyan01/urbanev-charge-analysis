## 二、参数与业务规则（逐接口）

### 2.1 公共查询参数（`QueryParams` 统一校验）
| 参数 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `startDate` | String | `yyyy-MM-dd`，正则校验 | 起始日期 |
| `endDate` | String | `yyyy-MM-dd`，且 `>= startDate` | 结束日期 |
| `hourRange` | String | 形如 `8-18`，`@Pattern`；起始 ≤ 结束 | 小时区间 |
| `zoneId` | String | `@Size(max=10)` | 分区编号（字符串） |
| `priceType` | String | 枚举 TOU / FLAT | 电价类型 |
| `limit` | int | `@Min(1) @Max(100)`，默认 10 | 返回条数上限 |

> 校验失败统一抛 `BusinessException.paramError("limit 最大值为 100")` → `code 400`。
> 实测：`?limit=999` → `{"code":400,"message":"limit 最大值为 100"}`。

### 2.2 逐接口要点

**#4 `/dashboard/kpi`** —— 首页 6 个指标卡
- 逻辑：取 `dashboard_kpi` 最新一行（`ORDER BY dt DESC LIMIT 1`）+ 取分区桩数 TOP6 作 `regions[]`。
- 实测：`stationCount=275, pileCount=23441, avgOccupancy=0.4587, totalVolume=904822.6, avgDuration=2.8765, imbalanceZones=23`。
- **注意**：`avgOccupancy` 是 0-1，前端自己 ×100。

**#5 `/zones`** —— 分区下拉 + 列表
- 逻辑：`ORDER BY avg_occupancy DESC LIMIT ?`，`total` 单独 `COUNT(*)` 返回 275（**不是当前页条数**）。
- 实测：`total=275`，返回 6 条（limit 默认 6）。

**#7 `/zones/{zoneId}`** —— 分区详情
- 逻辑：查 `v_zone_occupancy` 拿基础信息（不存在 → 404「分区 999 不存在」），再查 `v_zone_hour_profile` 按 `avg_occupancy DESC LIMIT 5` 拿峰时。
- 实测：zone 140 → 峰时 18/17/19/12/13 点。

**#8 `/charts/hourly`** —— 24h 供需曲线
- 逻辑：`hourRange` 过滤 + 按 `hour_of_day` 升序；`gap = demand_share - supply_share`，`imbalance` 取库里的值（E 岗口径）。
- 边界：`hourRange=19-17` → 400「hourRange 起始小时不能大于结束小时」。

**#9 `/charts/imbalance`** —— 失衡 TOP
- 逻辑：`ORDER BY imbalance DESC LIMIT ?`；`rank_no` 用**数据库里的排名**而不是重新算，保证与 E 岗口径一致。
- 实测：limit=10 返回 10 行，KPI 的 23 是总数（两者不冲突）。

**#10 `/charts/price-elasticity`** —— 电价双曲线
- 逻辑：`price_type` 分 TOU/FLAT 两组各 24 点，Service 里组装成 `{TOU:[], FLAT:[]}`。
- 为什么不在 SQL 里拼一个宽表：**前端 ECharts 要两条 series，后端返回两组数组最直接**，避免前端再 split。

**#11 `/charts/forecast`** —— 预测 vs 实际
- 逻辑：按 `zoneId` 取 168 行（7 天 × 24 小时），`mape` 单独算一次（公式 `avg(|predict-actual|/actual)`）。
- 边界：库里只有 140/145/152 三个分区有预测，其它分区 → 404「该分区暂无预测数据」。

**#12 `/charts/suggestions`** —— 布点建议
- 逻辑：`ORDER BY priority ASC LIMIT ?`，`reason` 原样返回（E 岗已生成完整中文句）。
- **注意**：`suggestedPiles` 是"建议新增"，不是总数。

**#15 `/dictionary`** —— 数据字典
- 逻辑：查 `data_dictionary` 全表（12 行），前端渲染成"数据源说明"页。

**#16 `/system/cache-stats`** —— 缓存自证
- GET：返回 `type/hitCount/missCount/hitRate/hitAvgMs/missAvgMs/speedup/localEntries`。
- POST `/reset`：清空计数器（答辩演示前先 reset，再跑 10 次请求，数字最干净）。

## 三、分层落地（每个接口都走这条路）

```
ChartController            ← 只做三件事：接参数、调 Service、包 ApiResponse
   │  @GetMapping("/charts/hourly")
   ▼
ChartService               ← 业务规则在这里：区间校验、gap 计算、组装双曲线
   │  @UevCache(prefix="chart:hourly", ttl=120)   ← 缓存切面打在这一层
   ▼
ChartMapper (接口)          ← 只有方法签名
   ▼
ChartMapper.xml (SQL)      ← 只 FROM v_hourly_supply_demand
   ▼
MySQL 视图 → ADS 表
```

**Controller 里没有一行 SQL，Mapper 里没有一行业务判断。** 这是 D01 分层规范的红线，D06 是它的落地证据。
