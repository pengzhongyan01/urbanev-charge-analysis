## 一、工程化五条（每条都有落地证据，不是口号）

| # | 条目 | 具体做法 | 落地证据 |
|---|---|---|---|
| 1 | **统一响应** | 所有接口返回 `{code,message,data,timestamp}`，用 `ApiResponse` 一处定义 | `ApiResponseTest` 3 例全绿；D10 16 张界面截图格式一致 |
| 2 | **统一异常** | 11 类异常收敛到 `GlobalExceptionHandler`，Service 只抛 `BusinessException` | D02 异常矩阵 + D13 六条实测异常 |
| 3 | **参数校验** | `@Valid` + `QueryParams.validate()` 双层校验，非法即 400 中文提示 | `QueryParamsTest` 4 例全绿；`?limit=999` 实测 400 |
| 4 | **日志审计** | `QueryLogInterceptor` 把每次请求写进 `query_log`（路径/耗时/是否命中缓存） | D07 `03_query_log.txt` 原始 10 行记录 |
| 5 | **单元测试** | JUnit 5，**7 例全绿**，覆盖响应结构与参数校验两块核心 | `mvn test` → `Tests run: 7, Failures: 0, Errors: 0` |

> **为什么只测了 7 例不测 70 例**：单测的价值在"锁住最容易改坏的契约"，不是刷数量。
> 响应四字段、缓存指纹、参数边界这三块是"改一行就可能全线崩"的地方，所以优先测这三块；
> 其余逻辑靠 D10 的接口级断言 + 冒烟脚本覆盖。**这叫测在刀刃上。**

## 二、7 个单测逐条说明

### `ApiResponseTest`（3 例）

| 测试方法 | 断言什么 | 为什么必须测 |
|---|---|---|
| `okShouldBeBusinessSuccess` | `ok()` 的 code=200、message=success、timestamp 非空 | 全站 16 个接口都靠这一个方法，它错了全线错 |
| `failShouldCarryErrorCode` | `fail()` 的 code 跟 `ErrorCode` 一致、data 为 null | 防止"失败响应带数据"导致前端误判成功 |
| `jsonMustContainFourFields` | 序列化后**恰好 4 个字段** | 字段一多一少，C 岗的 `common.js` 解析就可能出问题 |

> 第三个测试的写法有点"笨"：把 JSON 去掉花括号后按逗号数段数，等于 4 就算过。
> 这种写法简单但有效 —— 它真的能抓到"有人偷偷加了第 5 个字段"。

### `QueryParamsTest`（4 例）

| 测试方法 | 断言什么 | 为什么必须测 |
|---|---|---|
| `fingerprintStable` | 同参数两次指纹相同 | 指纹不稳定 → **缓存永远命中不了**，性能优化白做 |
| `fingerprintChangesWithFilter` | 改 `zoneId` 或 `hourRange`，指纹必须变 | 指纹不敏感 → **换个筛选还拿旧数据**，是最严重的正确性 bug |
| `startAfterEndShouldFail` | `startDate > endDate` 抛 400 | 错误应在校验层拦下，不该让 SQL 去查一次空结果 |
| `hourRangeParse` | `"17-19"` → `from=17, to=19` | 解析错位会让图表少画几小时，肉眼不易发现 |

> `fingerprintStable` + `fingerprintChangesWithFilter` 这两条是一对：
> **一个防"该同的没同"，一个防"该异的没异"**。只写其中一条等于没测。

**实测输出**：
```
Tests run: 7, Failures: 0, Errors: 0, Skipped: 0
BUILD SUCCESS
```

## 三、目录规范（新增代码往哪放）

```
com.uev
├── UevApplication.java         启动类
├── common/                     ← 全站基础设施（响应体、错误码、异常、查询参数）
│   ├── ApiResponse.java  ErrorCode.java  BusinessException.java
│   ├── GlobalExceptionHandler.java  QueryParams.java
├── config/                     ← 容器级配置（拦截器、CORS、缓存）
│   ├── WebConfig.java  AuthInterceptor.java  QueryLogInterceptor.java
│   ├── CacheService.java  HybridCacheService.java  CacheConfig.java
├── aspect/                     ← 切面（缓存注解 + 上下文）
│   ├── UevCache.java  CacheAspect.java  CacheContext.java
├── auth/                       ← 鉴权（JWT + BCrypt）
│   ├── JwtUtil.java  AuthService.java  LoginRequest.java  LoginResponse.java
├── controller/                 ← 只接参、调 Service、包响应（16 端点 / 6 个类）
├── service/                    ← 业务规则 + 缓存注解（5 个类）
├── mapper/                     ← MyBatis 接口（5 个，只有方法签名）
├── entity/                     ← 与视图字段一一对应（11 个）
└── vo/                         ← 与接口 data 一一对应（13 个）
resources/
├── application.yml             ← 配置（端口/数据源/缓存/JWT），无硬编码密码
└── mapper/*.xml                ← SQL（5 份，只 FROM v_*）
```

**两条硬规矩**：
1. `controller` 里**不许出现 SQL、不许出现 `if` 业务判断**（超 3 行的逻辑必须下沉 Service）。
2. `mapper/xml` 里**不许出现业务计算**（`gap`、`deviation`、`mape` 都已在 ADS 层算好）。

## 四、新增一个接口要改哪几个文件（清单）

以"新增 `/charts/peak-hours`"为例，**7 步，不多不少**：

| 步 | 文件 | 改什么 |
|---|---|---|
| 1 | `db/mysql/03_views.sql` | 若无现成视图，先建 `v_xxx`（或复用已有视图） |
| 2 | `mapper/ChartMapper.java` | 加方法签名 `List<Xxx> selectPeakHours(...)` |
| 3 | `resources/mapper/ChartMapper.xml` | 加 `<select>`，**只 FROM 视图** |
| 4 | `entity/Xxx.java` | 加实体（字段=视图字段的下划线转驼峰） |
| 5 | `service/ChartService.java` | 加方法 + `@UevCache(prefix="chart:peak", ttl=120)` |
| 6 | `controller/ChartController.java` | 加 `@GetMapping`，包 `ApiResponse.ok(...)` |
| 7 | `D05/mock/NN_xxx.json` + `D09/接口文档.md` + `D10 Postman` | 三处文档同步（缺一处就是"契约不同步"） |

> **第 7 步最容易被跳过，也最容易被扣分**。接口改了文档不改，等于把坑留给 C 岗和答辩当天的自己。

## 五、配置与安全（不许硬编码）

| 项 | 做法 | 反例（参考作业的硬伤） |
|---|---|---|
| 数据库密码 | `application.yml` 用 `${UEV_DB_PASSWORD:默认}`，可被环境变量覆盖 | 明文写死在 Java 里 |
| JWT 密钥 | `${UEV_JWT_SECRET:默认}` + **启动校验 ≥32 字节** | `secret = "123456"` |
| 端口/地址 | `server.port` 可命令行覆盖（`--server.port=18080`） | 写死 8080 且不可改 |
| 路径 | 无绝对路径（D 盘路径只出现在文档说明里） | `D:\一系列作业\...` 硬编码 |
| 日志 | 不打明文密码、不打 token 全文 | `log.info("password=" + pwd)` |

## 六、这份工程化说明了什么（结论）

> 7 个单测只覆盖"最容易被改坏的三个契约点"，却能在任何人动 `ApiResponse`、`QueryParams`、缓存 Key 时立刻报警；
> 两条分层红线（Controller 无 SQL、Mapper 无业务计算）保证"改一层不会牵动另一层"；
> 新增接口有固定 7 步清单，包含"文档三处同步"这一步，避免代码先行、文档脱节。

**如果要给一个数字**：63 个源文件、16 个接口、7 个单测、5 份 SQL 映射，
**没有一处明文密钥、没有一处绝对路径、没有一张 IDE 截图当代码。**
