# UrbanEV 后端分层规范（D01）

> 维护人：杨姗姗（D 岗）　|　版本 v1.0　|　2026-11-20
> 适用范围：`backend/` 全部代码。**后面 D02 ~ D15 的所有代码都按这份规范写**，组长拿这份文件就能判断代码合不合规。

---

## 一、为什么要分层（不是形式主义）

后端只有 16 个只读接口，真正的风险不是"写不出来"，而是三件事：

1. **前端一改字段名，后端就要搜遍全项目** —— 所以字段映射只在 Service 层做一次；
2. **MySQL 挂了 / Redis 挂了，接口跟着 502** —— 所以降级逻辑集中在 Service 与 CacheService，Controller 不碰；
3. **报告里贴不出"真代码"** —— 所以代码必须短、职责必须单一，一段 30 行的 Controller 直接贴进论文第三章才好看。

分层带来的直接收益：**出问题时你能一句话定位是"参数没校验"（Controller）、"口径算错"（Service）还是"SQL 查错表"（Mapper）。**

## 二、四层职责（谁能做什么，谁绝对不能做什么）

```
HTTP 请求
   │
   ▼
┌─────────────────────────────────────────────────────────────┐
│ Controller 层   com.uev.controller                            │
│ 只做三件事：接参数 → 调 Service → 包 ApiResponse              │
│ ✅ 允许：@GetMapping/@PostMapping、@Valid、@PathVariable        │
│ ❌ 禁止：写 SQL、写 if-else 判空、写 try-catch、写业务计算       │
│ 典型长度：一个方法 3 行                                       │
└─────────────────────────────────────────────────────────────┘
   │
   ▼
┌─────────────────────────────────────────────────────────────┐
│ Service 层   com.uev.service                                  │
│ 业务编排：参数语义校验、字段改名、补 summary、算相关系数、      │
│         缓存注解、降级决策、抛 BusinessException               │
│ ✅ 允许：@Service、@UevCache、BeanUtils.copyProperties          │
│ ❌ 禁止：出现 HttpServletRequest / ApiResponse（不能感知 HTTP） │
│ 典型长度：一个方法 5~30 行                                     │
└─────────────────────────────────────────────────────────────┘
   │
   ▼
┌─────────────────────────────────────────────────────────────┐
│ Mapper 层   com.uev.mapper + resources/mapper/*.xml           │
│ 只做一件事：把 SQL 结果映射成对象                              │
│ ✅ 允许：单表/视图查询、<if> 动态条件、LIMIT                   │
│ ❌ 禁止：业务判断、多表复杂 JOIN（口径在数仓层算，不在这算）     │
│ ❌ 禁止：直连 ads 表 —— 一律通过 v_* 视图（D08）               │
└─────────────────────────────────────────────────────────────┘
   │
   ▼
┌─────────────────────────────────────────────────────────────┐
│ Entity / VO 层   com.uev.entity / com.uev.vo                  │
│ Entity = 数据库一行；VO = 接口一个字段集合                     │
│ 两者不混用：Entity 里有 id，VO 里绝不能出现 id                 │
└─────────────────────────────────────────────────────────────┘
```

**依赖方向铁律：Controller → Service → Mapper → DB，单向。**
反向依赖（Mapper 调 Service、Service 调 Controller）一律视为错误，评审直接打回。

## 四、五条红线（违反任意一条，这一项就算没做）

### 红线 1：Controller 里不许出现 SQL 和 try-catch
```java
// ❌ 错误示范（参考作业里常见）
@GetMapping("/kpi")
public Map<String,Object> kpi() {
    try {
        return jdbcTemplate.queryForMap("select * from dashboard_kpi");
    } catch (Exception e) { return null; }   // 吞异常 → 前端白屏
}

// ✅ 正确示范（本项目实际代码，3 行）
@GetMapping("/kpi")
public ApiResponse<KpiVO> kpi(@Valid QueryParams params) {
    return ApiResponse.ok(kpiService.getKpi(params));
}
```

### 红线 2：Service 不许感知 HTTP
Service 方法签名里出现 `HttpServletRequest`、`HttpServletResponse`、`ApiResponse` 都是错的 —— 这样 Service 就没法写单元测试，也没法被定时任务复用。

### 红线 3：Mapper 不许直连 ADS 表
只查 `v_*` 视图（D08）。理由：口径在 B 岗那边变，改视图定义即可，你的 Mapper XML 一行都不用动。实测 `KpiMapper.xml` 里只有 `FROM v_kpi_overview`。

### 红线 4：不许硬编码配置与密钥
- 数据库地址、密码、Redis 密码、JWT 密钥 → 全部 `${ENV:默认值}` 形式；
- 不许出现 `D:\...`、`C:\Users\...` 这类绝对路径；
- 不许把真实密码写进代码或 SQL 脚本（演示数据里的密码是 **BCrypt 密文**，不是明文）。

对应参考作业的两条硬伤："6 处明文密钥"、"绝对路径硬编码 D 盘"。

### 红线 5：不许返回裸对象
所有 Controller 方法返回 `ApiResponse<T>`，不允许直接返回 `List`、`Map` 或 Entity。前端只判断 `code === 200`，裸返回会让前端拿不到 code。

## 五、命名规范

| 对象 | 规则 | 例子 |
|---|---|---|
| 接口路径 | 全小写、复数资源、kebab-case | `/api/charts/price-elasticity` |
| Controller 方法 | 动词或资源名，小驼峰 | `kpi()` `occupancy()` `priceElasticity()` |
| Service 方法 | `get` 开头 + 名词 | `getHourly()` `getImbalance()` |
| Mapper 方法 | `select` + 名词 | `selectImbalanceTop()` |
| Entity 类 | 与表名对应的大驼峰 | `zone_occupancy` → `ZoneOccupancy` |
| VO 类 | 语义 + VO 后缀 | `KpiVO` `PriceElasticityVO` |
| 接口字段 | 小驼峰，与契约 03 逐字一致 | `avgOccupancy` `suggestedPiles` |
| 数据库列 | 下划线 | `avg_occupancy` `suggested_piles` |
| 常量 | 全大写 + 下划线 | `DEFAULT_IMBALANCE_LIMIT` |

**字段名以契约 03 为唯一事实源。** 数据库列名和接口字段名不一致时（例如 `avg_demand` → `demandShare`），**只在 Service 层转一次**，禁止让前端改。

## 六、配置外部化规范

`application.yml` 里所有可变项都写成 `${环境变量:默认值}`：

```yaml
spring:
  datasource:
    url: jdbc:mysql://${MYSQL_HOST:localhost}:${MYSQL_PORT:3306}/${MYSQL_DB:uev_charge}?...
    password: ${MYSQL_PASSWORD:uev123456}
uev:
  jwt:
    secret: ${JWT_SECRET:uev-local-dev-secret-key-please-change-in-prod-2026}
  cache:
    type: ${CACHE_TYPE:auto}
  data:
    region-count: ${DATA_REGION_COUNT:275}
```

三条要求：
1. **换机器只改环境变量，不改代码**（D14 验证的就是这条）；
2. 密钥类必须有默认值但**默认值只能是本地开发用**，生产必须覆盖；
3. `region-count` 必须是 **275**（骨架里原本写的是 96，契约 03 专门标注了这个坑）。

## 七、日志规范

| 场景 | 级别 | 内容要求 |
|---|---|---|
| 启动 | INFO | 端口、缓存模式、鉴权开关（启动时打印，方便截图） |
| 缓存命中/未命中 | DEBUG | key、耗时（答辩演示时开 DEBUG 给老师看） |
| 业务异常（400/401/404） | WARN | code + message，**不打堆栈**（可预期的错误刷堆栈会把日志淹掉） |
| 降级（Redis/MySQL 不可用） | WARN | 哪个组件、什么原因、切到了什么模式 |
| 未预期异常 | ERROR | 完整堆栈（只有这里允许打堆栈） |

**禁止 `System.out.println`；禁止空 catch 块；禁止 `e.printStackTrace()`。**
参考作业的第 9 条硬伤就是"日志模块半成品，全是 pass"。
