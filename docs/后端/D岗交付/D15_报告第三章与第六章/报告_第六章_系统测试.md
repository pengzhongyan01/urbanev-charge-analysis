## 6.1 测试目标与环境

### 6.1.1 测试目标

本章回答四个问题：

1. 16 个接口是否按契约返回正确数据（功能正确性）；
2. 非法输入、错误路径、未认证请求是否以可读方式失败（健壮性）；
3. 缓存是否真实生效、提升多少（性能）；
4. Redis 缺失、MySQL 停机时系统是否仍可用（降级能力）。

## 6.2 测试方法与用例设计

### 6.2.1 三层测试结构

| 层次 | 手段 | 覆盖对象 |
|---|---|---|
| 单元测试 | JUnit 5，7 例 | 统一响应结构、查询参数校验与缓存指纹 |
| 接口测试 | Postman 集合 + 冒烟脚本 | 16 个接口的正常路径与断言 |
| 场景测试 | 手工构造 + 真实停机 | 参数异常、鉴权、缓存性能、依赖降级 |

### 6.2.2 用例设计原则

共设计 **43 条用例**（功能 17、安全 4、异常 8、性能 5、降级 4、工程 5），设计遵循三条原则：

1. **一接口一用例，只断言最易错点**：如 KPI 用例断言 `275 / 23441 / 0~1 比例`，而非"返回 200"。
2. **异常用例对准真实风险**：如"路径拼错必须 404 而非 500"，因 Spring Boot 3 默认会将路径不存在抛为 `NoResourceFoundException`，不处理即变 500。
3. **降级用例必须真停真测**：Redis 用例依托本机未部署 Redis 复现；MySQL 用例通过 `mysqladmin shutdown` 复现，不采用"注释代码模拟"。

## 6.4 健壮性与安全测试

### 6.4.1 异常场景

| 场景 | 请求 | 实测响应 |
|---|---|---|
| 参数越界 | `?limit=999` | `{"code":400,"message":"limit 最大值为 100"}` |
| 区间倒置 | `?hourRange=19-17` | `{"code":400,"message":"hourRange 起始小时不能大于结束小时"}` |
| 日期非法 | `?startDate=2025-13-01` | `code 400` |
| 资源不存在 | `/api/zones/999` | `{"code":404,"message":"分区 999 不存在"}` |
| **路径拼错** | `/api/hours/xx` | `{"code":404,"message":"接口不存在，请核对路径"}` |
| 方法不支持 | `POST /api/dashboard/kpi` | `code 405` |
| 未认证 | `/api/auth/me` 无头 | `{"code":401,"message":"未携带令牌，请先登录"}` |
| 密码错误 | 登录 wrong | `{"code":401,"message":"用户名或密码错误"}` |

全部响应为 HTTP 200 + body 内业务码，且**均不含 Java 堆栈**。

### 6.4.2 安全项

- 密码入库为 BCrypt 密文（`$2a$10$…`，60 字符），响应中不含该字段；
- 令牌被篡改或过期后调用受保护接口返回 401，不放行；
- 登录失败提示不区分"账号不存在"与"密码错误"，避免账号枚举；
- 配置中无明文密钥：数据库密码、JWT 密钥均支持环境变量覆盖，JWT 密钥启动校验 ≥32 字节。

## 6.5 性能测试

### 6.5.1 缓存性能

同一接口连续请求 1 次（回源）+ 5 次（命中）：

| 指标 | 未命中 | 命中 | 提升 |
|---|---|---|---|
| 服务端平均耗时 | 1.952 ms | 0.003 ms | 650.733× |
| HTTP 端到端 | 9.1 ms | 6.1 ms | 约 33% |
| `query_log` 记录 | 31 ms | 2~3 ms | 约 10× |

命中率 0.833（5/6）。`query_log` 中 `hit_cache` 字段记录了每次请求是否命中（0/1），使性能结论具备数据库级证据，而非仅凭接口自述。

> 口径说明：上表 1.952 ms → 0.003 ms（650.733×）取自 D07 的基准脚本（同批 6 次请求）；D10 的 Postman 界面截图在另一轮会话中自报 `0.005 ms vs 14.272 ms`（2667.596×，首次请求含建表缓存预热抖动）。两者量级一致（均为千倍级），报告正文统一引用 D07 的 650.733× 这一组，避免同一章出现两组不同倍数。

### 6.5.2 结果分析

端到端提升（33%）显著小于服务端提升（650×），原因是端到端耗时包含 HTTP 建连、JSON 序列化与前端反序列化等固定开销，缓存仅消除"查库与排序"环节。这一差异说明：**缓存优化的收益边界在数据库访问，不在网络传输**。若需进一步降低端到端耗时，应合并接口请求或压缩响应体，而非继续加缓存。

## 6.6 降级测试

| 场景 | 构造方式 | 系统行为 | 结论 |
|---|---|---|---|
| Redis 不可用 | 本机未部署 Redis，直接启动 | 启动日志 WARN"已自动降级为本地缓存，接口不受影响"；16 接口全部正常；`health.components.redis=DOWN` | 不影响可用性 |
| MySQL 停机·未缓存 | 停机后请求 `/charts/imbalance?limit=9` | `{"code":503,"message":"数据库暂时不可用，已降级返回"}` | 失败可读 |
| MySQL 停机·已缓存 | 停机前已缓存 KPI，停机后再请求 | `code=200`，返回停机前缓存数据 | 看板不整体瘫痪 |
| MySQL 停机·健康检查 | 停机后请求 `/health` | HTTP 200，`status=DEGRADED`，`mysql=DOWN` | 状态可见 |

启动耗时在降级路径下为 `Started UevApplication in 4.619 seconds`，即探活失败带来的额外开销不足 1 秒。

## 6.7 测试中发现并修复的问题

| # | 问题 | 现象 | 根因 | 处理 |
|---|---|---|---|---|
| 1 | 路径拼错返回 500 | `/api/hours/xx` → 500"服务器内部错误" | Spring Boot 3 抛 `NoResourceFoundException`，落到兜底 `Exception` 分支 | 在兜底处理器内判别该异常并转 404 |
| 2 | MySQL 停机返回 500 | 未命中请求 → 500 | `DataAccessException` 被兜底捕获 | 新增 `handleDataAccess` → 503 + 中文提示 |
| 3 | 命中耗时统计为 0 | `hitAvgMs=0.000`，无法自证 | `currentTimeMillis` 粒度粗，被四舍五入 | 改用纳秒累加后平均，得 0.003 ms |
| 4 | 缓存 Key 串号风险 | 不同 `limit` 可能命中同一 Key | Key 仅拼前缀 | Key 改为 `前缀 + MD5(方法名+全部入参)` |
| 5 | 前端收不到中文提示 | 参数错误时页面只显示 `HTTP 400` | 后端返回真实 HTTP 400，前端 `!res.ok` 提前抛错 | 统一改为 HTTP 200 + body 业务码 |
| 6 | PowerShell 启动中文乱码 | 日志与响应中文变 `?` | `-Dfile.encoding=UTF-8` 未加引号被拆成两段 | 启动参数加引号，并写入 D14 启动脚本 |

前 5 项均已修复并复测通过；第 6 项为部署侧问题，已固化到 `start.ps1` 与 D14 文档，避免换机复现。

## 6.8 测试结论

1. **功能**：16 个接口全部按契约返回，关键口径（275 分区、23441 桩、0~1 占用率、23 失衡分区）逐项对齐；43 条用例全部通过。
2. **健壮性**：参数、路径、鉴权、依赖四类异常均以"HTTP 200 + 中文业务码"失败，无堆栈泄露、无白屏。
3. **性能**：服务端缓存加速 650.733×，端到端提升约 33%，并由 `query_log.hit_cache` 提供可审计证据。
4. **降级**：Redis 缺失不影响任何接口；MySQL 停机按"已缓存可读 / 未缓存 503 / 健康检查 DEGRADED"三档处理，看板不整体瘫痪。

**局限说明**：性能数据为单机实测，非分布式压测；前端 UI 自动化测试由 C 岗负责，本章不覆盖。上述局限已在结论中如实标注，未作外推。
