# 第 3 章 系统设计

## 3.5 后端服务设计与实现

> 撰写人：D 岗 · 杨姗姗（学号 2400770293）　|　对应交付项：D01~D14　|　版本 v1.0

### 3.5.1 后端定位与职责边界

本系统后端位于"数据仓库 → 可视化"之间，承担三个职责：

1. **契约兑现**：把 ADS 层已算好的指标，按 `docs/contracts/03-接口规范.md` 约定的字段名、类型、口径原样暴露给前端；
2. **性能与稳定**：通过缓存与降级，把"批量导入型静态数据"的查询成本压到毫秒级，并在依赖故障时保住看板可用；
3. **可审计**：对每一次接口调用留痕（路径、耗时、是否命中缓存），使"性能提升"可被验证而非自述。

**明确不承担的职责**：不重算指标（口径归 E 岗《指标定义表》）、不造数据（数据由 B 岗 Sqoop 导出）、不做页面渲染（归 C 岗）。
这一边界是分层设计的前提，也是第 3.5.2 节包结构划分的依据。

### 3.5.2 技术选型与理由

| 项 | 选型 | 理由 |
|---|---|---|
| 框架 | Spring Boot 3.2.5 | 组内统一版本；3.x 原生支持 Jakarta、虚拟线程生态 |
| JDK | 17 | Spring Boot 3 最低要求；LTS 版本，答辩机器易部署 |
| 持久层 | MyBatis 3.0.3（`mybatis-spring-boot-starter`） | ADS 表字段多、查询以"按分区/按小时过滤 + 排序 + LIMIT"为主，手写 SQL 比 ORM 更可控；且能直接对接视图 |
| 缓存 | Spring Cache 抽象 + 自研 `HybridCacheService` | 需要"Redis 优先、本地兜底"的双模能力，原生 `RedisCacheManager` 做不到"连不上就降级" |
| 鉴权 | jjwt 0.12.5 + `spring-security-crypto` | 只要 JWT 签发校验与 BCrypt，不引入完整 Spring Security 过滤器链，减少配置复杂度 |
| 连接池 | HikariCP（Boot 默认） | 零额外依赖 |
| 测试 | JUnit 5 + MockMvc + 脚本冒烟 | 单测锁契约、脚本锁接口，两层互补 |

> **取舍说明**：未采用 MyBatis-Plus。其 CRUD 生成能力对"只读视图 + 复杂过滤"收益有限，
> 而版本适配（必须使用 `mybatis-plus-spring-boot3-starter`）反而增加踩坑面。这是一次有意的减法。

### 3.5.3 分层结构与包职责

```
com.uev
├── common/      统一响应、错误码、业务异常、全局异常处理、公共查询参数
├── config/      拦截器注册、CORS、缓存实现与探活
├── aspect/      缓存注解 @UevCache、切面、命中上下文
├── auth/        JWT 工具、登录服务、登录出入参
├── controller/  16 个端点（只接参、调 Service、包响应）
├── service/     业务规则、参数语义校验、缓存注解落点
├── mapper/      MyBatis 接口（仅方法签名）
├── entity/      与视图字段一一对应
└── vo/          与接口 data 一一对应
```

两条硬性分层约束：

1. **Controller 内不出现 SQL、不出现超过 3 行的业务判断**；一切业务规则下沉 Service。
2. **Mapper XML 内不出现业务计算**（`gap`、`deviation`、`mape` 等均已在 ADS 层算好），且**只允许 `FROM v_*` 视图**，不直连实体表。

这两条约束的直接收益是"改一层不牵动另一层"：B 岗调整视图口径时，只要视图名与字段名不变，D 岗 13 条 SQL 与 16 个接口零改动（详见 3.5.7）。

### 3.5.4 统一响应与异常处理

所有接口返回同一结构：

```json
{ "code": 200, "message": "success", "data": {...}, "timestamp": 1795160027232 }
```

`code` 取值 200/400/401/403/404/405/500/503。**HTTP 状态码恒为 200，业务成败由 body 内 `code` 表达**，原因在于前端请求封装（`frontend/js/common.js`）在 `!res.ok` 时直接抛出 `HTTP xxx` 并丢弃响应体：

```javascript
const res = await fetch(url);
if (!res.ok) throw new Error(`HTTP ${res.status}`);   // 若后端返回 400，中文提示在此丢失
const json = await res.json();
if (json.code !== 200) throw new Error(json.message); // 中文提示在此生效
```

因此"HTTP 200 + body 内业务码"不是不规范，而是与前端契约一致的必要设计。

异常处理采用"集中收敛"策略：Service 只抛 `BusinessException`（携带 `ErrorCode`），由 `GlobalExceptionHandler` 统一转换，共覆盖 11 类异常。其中两处为针对性补丁：

- `NoResourceFoundException`（Spring Boot 3 的"路径不存在"）显式转 404。若不处理，前端拼错一个路径就会得到 500，使"接口拼错"被误判为"后端崩溃"。
- `DataAccessException` 单独转 503 并附中文提示"数据库暂时不可用，已降级返回"。503 语义为"依赖暂不可用"，与 500"程序缺陷"区分，前端可据此提示"稍后重试"。

### 3.5.5 登录鉴权实现

流程：`POST /api/auth/login` → 按用户名查 `sys_user` → `BCryptPasswordEncoder.matches()` 校验 → 签发 HS256 JWT（`sub`=用户名、`role`=角色、有效期 2 小时）→ 前端后续请求携带 `Authorization: Bearer <token>` → `AuthInterceptor` 解析并写入 `AuthContext`。

四个设计决定：

1. **密码存 BCrypt 密文**：`sys_user.password_hash` 为 `VARCHAR(100)`，存 `$2a$10$…`（60 字符）。BCrypt 自带随机盐，同一密码每次哈希不同，可抵御彩虹表；`password_hash` 加 `@JsonIgnore`，任何响应均不返回该字段。
2. **密钥不硬编码**：`uev.jwt.secret` 从配置读取，支持环境变量覆盖；`JwtUtil` 构造时校验密钥 ≥ 32 字节，不足则启动失败——把"运行到第一次登录才炸"提前到"启动即炸"。
3. **拦截器顺序**：`OPTIONS` 预检请求必须在取令牌之前放行。否则跨域预检被 401，浏览器只显示一个与鉴权无关的 CORS 错误，排障成本极高。
4. **默认关闭鉴权**（`uev.auth.enabled=false`）：C 岗联调期不被登录阻塞；答辩演示时以 `--uev.auth.enabled=true` 启动，现场展示 401 → 登录 → 200 链路。

已知边界（主动声明）：未实现刷新令牌、角色级细粒度授权、令牌黑名单与登录失败次数限制。原因是本系统为单机演示型系统，工作量优先投向接口契约完备性与缓存/降级。

### 3.5.6 缓存设计与性能

**缓存模型**：`key = 前缀 + ":" + MD5(方法名 + 全部入参规范化串)`。使用 MD5 而非直接拼接参数，目的有三：控制 Key 长度、防止用户构造参数伪造 Key、使参数顺序无关。TTL 按数据更新频率分级：KPI 300s、分区占用率 600s、图表 120s、字典 300s；`/health`、`/auth/*`、`/system/*` 不缓存。

**双模实现**：`HybridCacheService` 支持 `auto / redis / local` 三种模式。`auto` 在启动时探活 Redis，失败则降级为本地 `ConcurrentHashMap` 并打印 WARN 级日志（"已自动降级为本地缓存，接口不受影响"）。启动耗时仅增加约 0.5 秒，换取"未部署 Redis 亦可运行"。

**三大经典问题的应对**：穿透——`notFound` 分支不写缓存，参数先校验；击穿——同一 Key 回源加分段锁；雪崩——TTL 加 ±10% 随机抖动。未引入布隆过滤器，因数据源为固定 275 个分区，不存在无限 Key 空间，引入反而增加一次哈希开销。

**实测性能**（同一接口 `GET /api/charts/imbalance?limit=7`，1 次回源 + 5 次命中）：

| 口径 | 未命中 | 命中 | 提升 |
|---|---|---|---|
| 服务端平均耗时 | 1.952 ms | 0.003 ms | 650.733× |
| HTTP 端到端耗时 | 9.1 ms | 6.1 ms | 约 33% |
| `query_log` 记录耗时 | 31 ms | 2~3 ms | 约 10× |

服务端 650 倍与端到端 33% 的反差需明确解释：缓存消除的是"查库与排序"这一段，而 HTTP 建连、JSON 序列化与反序列化是固定开销。**缓存省的是数据库，不是网络**。

计时采用纳秒累加后再平均，避免 `currentTimeMillis` 粒度导致命中耗时四舍五入为 0，从而使数据不可信。

### 3.5.7 数据访问与视图接入

后端共 5 个 Mapper、13 条 SQL，全部 `FROM v_*` 视图（唯一例外 `data_dictionary` 为人工维护的说明表）。字段命名约定为"库内下划线、VO 驼峰"，配合 `map-underscore-to-camel-case: true`，13 条 SQL 无需手写 `resultMap`。

SQL 写法四条约定：只用 `#{}` 不用 `${}`（防注入）、`<where>+<if>` 代替 `WHERE 1=1`、排序与 `LIMIT` 必须同时出现（否则结果集不稳定）、不在 SQL 内做业务计算。

**视图作为稳定接口的价值**已在实测中体现：将 `v_zone_occupancy` 的内部口径由"全期平均"改为"最近 30 天"后，后端的 Mapper、Service、Controller 与前端均零改动。

### 3.5.8 小结

本节实现的后端以"契约、缓存、降级"三条主线组织：契约保证 16 个接口字段与口径稳定可对齐；缓存把查询成本降到毫秒级并保留可审计证据；降级保证 Redis 缺失与 MySQL 停机时不整体瘫痪。分层约束（Controller 无 SQL、Mapper 无计算、只查视图）使后端可以在数据仓库口径变化时保持低改动成本。接口实测与异常场景验证见第 6 章。
