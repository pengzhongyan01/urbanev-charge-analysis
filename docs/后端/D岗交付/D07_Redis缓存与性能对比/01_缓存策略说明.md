> 维护人：杨姗姗（D 岗）　|　版本 v1.0　|　2026-11-20
> 实现：`HybridCacheService` + `@UevCache` 注解 + `CacheAspect` 切面　|　模式：Redis / 本地双模自动切换

## 一、为什么要做缓存（先讲问题）

看板的数据特性决定了它**天然适合缓存**：

| 事实 | 含义 |
|---|---|
| 数据来源是 ADS 层，**每天由 Sqoop 批量导入一次** | 同一天内查 1 次和查 100 次，结果完全一样 |
| 275 个分区 × 24 小时 = 6600 行画像，`ORDER BY` 排序 | 每次请求都在做重排，纯浪费 |
| 答辩现场 6 个页面 + 10 张图同时刷新 | 无缓存 = 瞬时几十次重复查询 |
| 老师会问"你们后端有什么亮点" | **"同一接口缓存前后 650 倍"** 比"我写了很多接口"有力得多 |

## 二、Key 设计（防串号的关键）

```
key = prefix + ":" + MD5(方法名 + 全部入参的规范化字符串)
```

例：
```
uev:chart:imbalance:a3f9c1e2b7d4...   ← /charts/imbalance?limit=10&startDate=null
uev:chart:imbalance:8b2c4f1a9e6d...   ← /charts/imbalance?limit=23&startDate=null
```

**为什么用 MD5 而不是直接拼参数**：
1. **长度可控**：Redis Key 太长会拖慢比较；多个参数拼起来可能上百字符。
2. **防注入式 Key**：用户传 `zoneId="140:limit=999"` 时，直接拼会伪造出另一个 Key；MD5 后不可能撞。
3. **参数顺序无关**：Service 层把参数按字段名排序后再拼，`{a:1,b:2}` 与 `{b:2,a:1}` 得到同一 Key。

> 这是一个"看起来简单、其实最容易出事"的点。写进报告，老师会觉得你想过。

## 三、TTL 设计（每个数字都有依据）

| 缓存前缀 | TTL | 依据（契约 03 原话 + 业务判断） |
|---|---|---|
| `uev:kpi:*` | **300s**（5 分钟） | KPI 是汇总数，变化最慢；5 分钟内答"275 个站 / 23441 个桩"不会错 |
| `uev:zone_occ:*` | **600s**（10 分钟） | 地图散点 275 条，最重的一次查询；10 分钟内的占用率波动对看板无意义 |
| `uev:chart:*` | **120s**（2 分钟） | 图表要"看起来是活的"；2 分钟既省掉重复查询，又不会让老师觉得"数据是死的" |
| `uev:dict:*` | **300s** | 字典几乎不变，但没必要长驻 |
| `/health`、`/auth/*`、`/system/*` | **不缓存** | 健康检查必须实时；鉴权结果带用户态，缓存会串号；统计接口本身要看实时数 |

> **答辩话术**：TTL 不是拍脑袋，是按"数据更新频率"和"用户能容忍多旧"两头夹出来的。
> 数据每天导一次，TTL 却设 2 分钟，是为了**演示时能看到数字在动**，这是产品判断不是技术判断。

## 四、双模架构（Redis 挂了会怎样）

```
CacheService（接口）
   └── HybridCacheService（实现）
          ├── 模式 auto：启动时探活 Redis
          │     ├── 通 → 走 Redis（真正分布式缓存，多实例共享）
          │     └── 不通 → 落本地 ConcurrentHashMap（单机可用，接口照常）
          ├── 模式 redis：强制 Redis（探活失败直接抛，用于验证部署）
          └── 模式 local：强制本地（无 Redis 环境 / 答辩兜底）
```

配置：`uev.cache.type=auto|redis|local`，默认 `auto`。

**实测日志（`证据/04_Redis降级日志.txt` 原文）**：
```
WARN 19548 --- [uev-charge-analysis] [main] com.uev.config.CacheConfig :
[缓存] Redis 探活失败（Unable to connect to Redis），已自动降级为本地缓存，接口不受影响
INFO 19548 --- [uev-charge-analysis] [main] com.uev.UevApplication :
Started UevApplication in 4.619 seconds (process running for 5.125)
```
> **启动多花 0.5 秒，换来"没装 Redis 也能跑"**。这一句就是降级设计的全部价值。

## 五、性能实测（三次测量，三个口径）

### 5.1 服务端耗时：650 倍（最硬的数）

同一接口 `GET /api/charts/imbalance?limit=7`，从 `cache-stats` 自证：

```json
{
  "type": "local",
  "hitCount": 5,
  "missCount": 1,
  "hitRate": 0.833,
  "hitAvgMs": 0.003,
  "missAvgMs": 1.952,
  "speedup": 650.733,
  "localEntries": 10
}
```
- 未命中（回源 MySQL + 排序）：**1.952 ms**
- 命中（本地 Map 取对象）：**0.003 ms**
- **加速比 650.733×**，命中率 83.3%（1 次回源 + 5 次命中）

> `hitAvgMs=0.003` 能测出来不是巧合：计时用 **纳秒累加**后再除，避免 `System.currentTimeMillis()`
> 粒度太粗被四舍五入成 0（如果显示 0.000，老师会怀疑你在造假）。

### 5.2 HTTP 端到端耗时：9.1ms → 6.1ms

```
第 1 次（未命中，回源查 MySQL）：9.1 ms
后续 5 次（命中缓存）：6.7 / 5.7 / 6.4 / 5.9 / 6.1 ms
平均命中：6.1 ms
```

**为什么服务端 650 倍，端到端只省 33%？** 这个反差必须主动解释，否则会被当成"吹牛"：
- 端到端 = 建连 + 序列化 + JSON 渲染 + 网络回环 + 反序列化；
- 服务端 1.952ms 里，**缓存省的只是"查库那一段"**；
- 剩下 6ms 是 **HTTP 与 JSON 的固定开销**，缓存对它无能为力。
> 一句话：**缓存省的是数据库，不是网络。** 说清楚这一点，比报一个大数字更可信。

### 5.3 query_log 记录：31ms → 2~3ms

```
id  api_path                 cost_ms  hit_cache  created_at
20  /api/charts/imbalance    31       0          2026-11-20 15:31:34   ← 回源
21  /api/charts/imbalance    13       1          2026-11-20 15:31:34   ← 首次命中（含 JIT 预热）
22  /api/charts/imbalance    3        1          2026-11-20 15:31:34
23  /api/charts/imbalance    2        1          2026-11-20 15:31:34
24  /api/charts/imbalance    3        1          2026-11-20 15:31:34
25  /api/charts/imbalance    2        1          2026-11-20 15:31:34
```
`hit_cache` 字段是切片最有力的证据：**不用我自证，数据库里就写着这次走没走缓存。**

## 六、缓存三大经典问题的应对（这题必被问）

| 问题 | 现象 | 我的做法 | 还没做的 |
|---|---|---|---|
| **缓存穿透** | 查不存在的 key，每次都打到库 | `notFound` 分支不写缓存 + 参数先校验（`zoneId` 不存在直接 404，不查库两次） | 布隆过滤器（数据源固定 275 个分区，收益不大） |
| **缓存击穿** | 热点 key 过期瞬间，几十个请求同时回源 | `HybridCacheService.load()` 里对同一 key 加 `synchronized` 分段锁，**同 key 只放一个线程回源** | 分布式锁（多实例才需要） |
| **缓存雪崩** | 大批 key 同时过期 | TTL 加 **±10% 随机抖动**（`ttl * (0.9 + random*0.2)`） | 多级缓存 |

> 写清"还没做的"很重要：老师问"为什么不用布隆过滤器"，答"数据源是固定的 275 个分区，不存在无限 key，
> 用了反而增加一次哈希开销"——这叫**有判断**，不是"没做"。

## 七、缓存切面怎么工作（代码逻辑）

```java
@Around("@annotation(uevCache)")   // 打在 Service 方法上
public Object around(ProceedingJoinPoint pjp, UevCache uevCache) throws Throwable {
    String key = buildKey(uevCache.prefix(), pjp);        // 前缀 + MD5(方法名+入参)
    Object cached = cacheService.get(key);
    if (cached != null) { CacheContext.markHit(); return cached; }   // 命中：标记 + 直接返回
    Object result = pjp.proceed();                        // 未命中：放行到 Service 查库
    cacheService.put(key, result, jitter(uevCache.ttl()));// 写回（TTL 带抖动）
    return result;
}
```

`CacheContext`（ThreadLocal）把"这次命中没命中"传给 `QueryLogInterceptor` 写进 `query_log.hit_cache`。
**这是切面与审计的串联点**，也是为什么 `query_log` 里能看到 `hit_cache=1`。

## 八、怎么复现这份数据（答辩前自己跑一遍）

```powershell
# 1) 启动（强制本地缓存，不依赖 Redis）
java -jar backend\target\uev-charge-analysis.jar --uev.cache.type=local

# 2) 清空统计
curl.exe -s -X POST "http://localhost:8080/api/system/cache-stats/reset"

# 3) 连打 6 次同一接口
1..6 | ForEach-Object { curl.exe -s -o NUL -w "%{time_total} `n" "http://localhost:8080/api/charts/imbalance?limit=7" }

# 4) 看统计（应看到 hitRate≈0.833、speedup 数百倍）
curl.exe -s "http://localhost:8080/api/system/cache-stats"
```
