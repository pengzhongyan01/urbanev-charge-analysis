# MySQL 表设计说明（D03）

> 维护人：杨姗姗（D 岗）　|　版本 v1.0　|　2026-11-20
> 库：`uev_charge`　|　引擎 InnoDB　|　字符集 utf8mb4　|　共 **14 张表 + 10 个视图**

---

## 一、设计总原则

1. **后端只读**：所有 ADS 类表由 B 岗 Sqoop 导出、E 岗直插，D 岗只 SELECT，不写业务数据（除 `sys_*` 与 `query_log`）。
2. **字段名用下划线**，接口字段用小驼峰，映射只发生在 MyBatis（`map-underscore-to-camel-case: true`）与 Service 层。
3. **时间类字段一律 VARCHAR**：`compute_time`、`forecast_date` 存字符串 —— 这是契约 04 点名提醒的坑，
   Hive `TIMESTAMP` 经 Sqoop 转 MySQL `DATETIME` 时区/格式经常对不上，存字符串最稳。
4. **一张 ADS 表 = 前端一个图表**（契约 04 的原话）。所以表的主键只是自增 id，业务唯一性靠 `zone_id` / `(zone_id, hour_of_day)` 保证。
5. **数值精度**：占用率、份额、偏差率一律 `DOUBLE`，**存 0-1 的比例不存百分数**（契约 03 强调"前端自己 ×100"）。

## 三、三个必须写进报告的设计决策

### 决策 1：`compute_time` / `forecast_date` 用 VARCHAR，不用 DATETIME
- **问题**：Sqoop 导出时 Hive `TIMESTAMP` → MySQL `DATETIME` 会因时区（Hive 默认 UTC，MySQL 连接串配 Asia/Shanghai）差 8 小时；
  而 `forecast_date` 在 Hive 里本来就是 `STRING`。
- **做法**：统一 `VARCHAR(20)/(30)` 存字符串，格式 `yyyy-MM-dd` / `yyyy-MM-dd HH:mm:ss`。
- **收益**：Sqoop 导出零类型映射错误，前端过滤用字符串比较也正确（ISO 格式天然可比较）。

### 决策 2：`sys_user.password_hash` 存 BCrypt 密文，长度 100
- **问题**：参考作业"6 处明文密码"是硬伤，老师一眼能看出来。
- **做法**：`VARCHAR(100)` 存 `$2a$10$...`（BCrypt 固定 60 字符，留余量给未来换 `$2b$`/argon2）；
  Java 侧用 `BCryptPasswordEncoder.matches()` 校验，**任何接口都不返回该字段**（`@JsonIgnore`）。
- **证据**：演示账号 `admin / uev123456` 在库里是 `$2a$10$AizSB.CVvR9Y0agOlJjXbeTzWi3CjUt4D3OA.TlDq4fqyMpVyWiJK`。

### 决策 3：索引按"实际查询方式"建，不按字段数量建
| 索引 | 建在 | 为什么 |
|---|---|---|
| `uk_zone` | `zone_occupancy.zone_id` | 分区唯一，且详情接口按 zoneId 精确查 |
| `uk_zone_hour` | `zone_hour_profile(zone_id, hour_of_day)` | 详情页查某分区 24 小时画像，联合唯一最省 |
| `uk_type_hour` | `price_elasticity(price_type, hour_of_day)` | 双曲线接口按类型取 24 点 |
| `idx_zone_hour` + `idx_rank` | `imbalance_index` | TOP 接口 `ORDER BY imbalance DESC LIMIT n`，rank_no 支持排名过滤 |
| `idx_priority` | `expansion_suggestion.priority` | 建议表按优先级排序 |
| `idx_created` + `idx_path` | `query_log` | 审计按时间倒序 + 按接口聚合缓存命中率 |
| `idx_occ` | `zone_occupancy.avg_occupancy` | 地图按占用率排序取热点 |

> **没有给每张表都加一堆索引**：ADS 表是"一次导入、多次读"，索引多了会拖慢 Sqoop 导入。
> 答辩讲这一句，比堆 20 个索引有说服力。

## 四、10 个视图（D08 的接入对象）

后端 Mapper 只查视图，不查表。视图名与字段名是 D 与 B/C 之间的稳定接口：

| 视图 | 被谁消费 | 说明 |
|---|---|---|
| `v_kpi_overview` | `KpiMapper.selectLatest` | KPI 快照 |
| `v_zone_occupancy` | `KpiMapper.selectRegions` / `ZoneMapper` | 分区下拉 + 地图 |
| `v_zone_hour_profile` | `ZoneMapper.selectZoneHourProfile` | 分区详情峰谷 |
| `v_hourly_supply_demand` | `ChartMapper.selectHourly` | 24h 曲线 |
| `v_imbalance_top` | `ChartMapper.selectImbalanceTop` | 失衡 TOP |
| `v_price_elasticity` | `ChartMapper.selectPriceByType` | 电价双曲线 |
| `v_forecast_series` | `ChartMapper.selectForecast` | 预测曲线 |
| `v_suggestions` | `ChartMapper.selectSuggestions` | 布点建议 |
| `v_volume_deviation` | `ChartMapper.selectVolumeDeviation` | 双口径偏差 |
| `v_poi_correlation` | `ChartMapper.selectPoiCorrelation` | POI 关联 |

**替换机制**：B 岗（B10）可以改视图内部定义（比如口径从"全期平均"改成"最近 30 天"），
只要**视图名和字段名不变**，D 岗所有 Mapper XML 一行都不用改。这就是"契约"的意义。

## 五、实测验证（本机 MySQL 8.0.45）

```sql
-- 导入后自查
SELECT COUNT(*), SUM(charge_count) FROM zone_occupancy;   -- 275 | 23441（与数据字典口径一致）
SELECT COUNT(*) FROM zone_hour_profile;                   -- 6600（= 275 × 24）
SELECT COUNT(*) FROM demand_forecast;                     -- 504（3 分区 × 7 天 × 24 小时）
SHOW FULL TABLES;                                         -- 14 BASE TABLE + 10 VIEW
```

导入过程中踩到的一个坑（写进 RUNBOOK 给 A 岗）：
**`mysql -e "source X.sql"` 遇到中文路径会报 `Failed to open file`**，
把脚本放到纯英文路径（如 `C:\temp\sql\`）再 source 即可。
