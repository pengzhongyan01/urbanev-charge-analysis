# 异常降级证据（D13）

> 维护人：杨姗姗（D 岗）　|　版本 v1.0　|　实测时间 2026-11-20 15:31~15:36　|　环境：本机 Windows + MySQL 8.0(3307) 临时实例

---

## 一、三类故障，一张表看完

| 故障 | 怎么造的 | 系统行为 | 用户看到什么 | 结论 |
|---|---|---|---|---|
| **Redis 不可用** | 本机不装 Redis，直接启动 | 启动探活失败 → 自动降级本地缓存 | 一切正常，只是 `health` 里 `redis=DOWN` | **不影响任何接口** |
| **MySQL 停机** | `mysqladmin shutdown` 停掉 3307 实例 | `health` 仍 200 但 `mysql=DOWN`；未命中缓存的查询 → 503；已缓存 → 正常返回 | 状态灯变"部分组件异常"，个别图空 | **不整体瘫** |
| **非法参数 / 错路径 / 无令牌** | 手工构造请求 | 统一 `{code,message}`，中文提示 | 页面弹一行中文，不白屏 | **失败可读** |

## 二、Redis 不可用（降级，不是崩溃）

### 日志原文（`证据/04_Redis降级日志.txt`）
```
2026-11-20T15:32:27.329+08:00  WARN 19548 --- [uev-charge-analysis] [main] com.uev.config.CacheConfig :
[缓存] Redis 探活失败（Unable to connect to Redis），已自动降级为本地缓存，接口不受影响

2026-11-20T15:32:27.799+08:00  INFO 19548 --- [uev-charge-analysis] [main] com.uev.auth.JwtUtil :
[鉴权] JWT 初始化完成，令牌有效期 8 小时

2026-11-20T15:32:28.571+08:00  INFO 19548 --- [uev-charge-analysis] [main] com.uev.UevApplication :
Started UevApplication in 4.619 seconds (process running for 5.125)
```

### 三个关键点
1. **级别是 WARN 不是 ERROR**：这不是故障，是"换了个地方缓存"，用 ERROR 会让运维误报警。
2. **启动没有被阻塞**：探活用超时（毫秒级），失败立刻走本地，`Started ... in 4.6s` 说明多花不到 0.5 秒。
3. **一句话说清后果**：日志里直接写"接口不受影响"，运维看到这行就不用去查了。

### 系统行为
- `GET /api/health` → `status=UP`（若 MySQL 正常）或 `DEGRADED`，`components.redis=DOWN`
- 所有查询接口**照常返回**，只是缓存落在 `ConcurrentHashMap`
- 缓存统计里 `type` 从 `redis` 变 `local`（`/api/system/cache-stats` 可见）

## 三、MySQL 停机（三档降级）

### 停库后的三个实测响应（`证据/06_MySQL降级.txt` 原文）

**① health 仍 200，但明确告知组件状态**
```json
{"code":200,"message":"success","data":{
  "status":"DEGRADED","timestamp":"2026-11-20T15:35:36",
  "application":"uev-charge-analysis","version":"1.0.0","regionCount":275,
  "components":{"mysql":"DOWN","redis":"DOWN"}},"timestamp":1795160136373}
```
> 注意 `regionCount` 仍返回 275（来自配置，不是查库），所以健康检查**不会因为库挂了就查不出东西**。

**② 未命中缓存的查询 → 503 + 中文提示**
```json
{"code":503,"message":"数据库暂时不可用，已降级返回","timestamp":1795160141491}
```
- 是 **503 不是 502/500**：503 语义是"服务暂时不可用"，前端可以据此显示"稍后重试"而不是"系统故障"。
- 是 **HTTP 200 + body 503**：前端能拿到中文提示（见 D02 第一节）。

**③ 已缓存的数据仍能返回**
> 停机前已经缓存过的 KPI、分区列表、图表数据，继续从内存返回，**看板不会整体黑掉**。
> 这就是"缓存不只是快，还是故障时的缓冲垫"。

### 为什么这三档是对的
```
库挂了
 ├── 缓存有 → 返回旧数据（用户几乎无感）
 ├── 缓存无 + 可探活 → health 报 DOWN（运维知道）
 └── 缓存无 + 需查数 → 503 + 中文（用户知道该等）
```
**没有一档是"白屏"或"500 加一堆堆栈"。**

## 四、参数/路径/鉴权类异常（`证据/01_异常场景.txt`）

| 场景 | 请求 | 返回 |
|---|---|---|
| 参数越界 | `?limit=999` | `{"code":400,"message":"limit 最大值为 100"}` |
| 资源不存在 | `/api/zones/999` | `{"code":404,"message":"分区 999 不存在"}` |
| 路径拼错 | `/api/hours/xx` | `{"code":404,"message":"接口不存在，请核对路径"}` |
| 区间反了 | `?hourRange=19-17` | `{"code":400,"message":"hourRange 起始小时不能大于结束小时"}` |
| 无令牌 | `/api/auth/me` | `{"code":401,"message":"未携带令牌，请先登录"}` |
| 密码错 | 登录 wrong | `{"code":401,"message":"用户名或密码错误"}` |

全部 HTTP 200 + 中文 `message`，**没有一条返回 Java 堆栈**。
其中 `/api/hours/xx` 这条最能说明功夫：Spring Boot 3 默认把它抛成 `NoResourceFoundException`，
不处理会变成 500「服务器内部错误」—— 一个拼错的路径就会让老师以为后端崩了。

## 五、结论（可直接进报告）

> 本系统对"依赖不可用"做了三层降级：
> 缓存层 Redis 挂了自动落本地（启动耗时仅增 0.5s，接口零影响）；
> 数据层 MySQL 挂了按"已缓存可返回 / 未缓存返 503 / 健康检查报 DEGRADED"三档处理，看板不整体瘫痪；
> 请求层非法参数、错路径、未认证一律返回 HTTP 200 + 中文 `code/message`，前端不会白屏。
> 三类故障均为**真停真测**，原始日志与响应见 `证据/`。

### 答辩可能被追问
1. **"503 为什么不是 500？"** —— 500 是"程序有 bug"，503 是"依赖暂时不可用"。语义不同，前端处理也不同。
2. **"库挂了还返回旧数据，会不会误导？"** —— 会，所以 `health` 明确报 `DEGRADED`，页面状态灯会变；数据可看但状态可见，这是可接受的取舍。
3. **"为什么不做熔断？"** —— 数据源是单库 + 批量导入，没有下游服务链，熔断收益不大；本地缓存已经承担了缓冲作用。
