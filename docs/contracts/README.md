# 契约（Contracts）机制

> **这个目录是全组唯一的"事实来源"（Single Source of Truth）。**
> 所有人遇到"这个字段叫什么""这个指标怎么算""这个接口返回什么"的问题时，**不要互相问，去这里看**。

---

## 一、为什么要有契约目录

我们的痛点：如果 B 需要知道 E 的指标口径、D 需要知道返回哪些字段、C 需要知道图表数据长什么样，
靠"微信问一句"会出三个问题：
1. 答案散落在聊天记录里，**找不到**
2. 同一个人在不同时间可能给出**不一致的答案**
3. 有人漏问，或者问了没回，**下游卡住却没人知道**

**契约目录把这些问题一次性解决**：
- 答案固定写在文件里，**版本化、可追溯**
- 任何人改契约都是一次 git commit，**所有人 pull 就能看到**
- 改契约 = 改代码 = 要评审，**不能偷偷改**

## 三、契约变更规则（唯一硬规矩）

### 规则 1：改契约 = 提 PR + 组长评审

`docs/contracts/` 目录受保护，任何人**不能直接改 main 分支**上的契约文件。

```
流程：
  1. 从 main 拉新分支：git switch -c contract/指标定义-v2
  2. 修改 docs/contracts/02-指标定义表.md
  3. 提交：git commit -m "[契约] 指标定义表 v2 - 供需失衡指数口径调整"
  4. 推送并提 PR，@ 组长
  5. 组长评审通过 → 合并 → 其他人 pull 即生效
```

### 规则 2：契约文件头必须带版本号和变更记录

每份契约文件开头长这样：

```markdown
> **版本**：v1.3
> **最后修改**：2026-11-25 by E
> **变更记录**：
> - v1.3 (11-25) 修正供需失衡指数的基准口径：全市同期 → 同类型分区同期
> - v1.2 (11-24) 新增峰谷差 PK 指标
> - v1.1 (11-22) 补充第 5-8 项指标定义
```

**为什么要记变更记录**：
下游（比如 B）pull 到新版本时，看一眼变更记录就知道"我的实现要不要跟着改"，
**不用再去问 E**。

### 规则 3：下游发现契约有问题 → 提 issue 或直接改契约 PR，不私聊

在群里的对话只用来**通知**，不作为契约来源。
例：
> "[契约] E 更新了指标定义表到 v1.3，B 记得 pull 一下，DWS 层可能要加个字段"

这句话 + 一次 git pull = 完成交接。**契约文件本身才是交接物，聊天只是提醒。**

### 规则 4：契约里的表名、字段名必须和代码一致

- 契约里的指标名 → B 的 SQL 里必须用同一个名字
- 契约里的接口路径 → D 的 Controller 必须完全一致
- C 的前端调用路径必须来自 `03-接口规范.md`，**不能自己发挥**

`scripts/check-contracts.sh` 会自动检查这几处一致性，**检查不过不能合并**。

## 四、每天怎么用（30 秒）

```bash
# 开工第一件事：拉最新契约和代码
bash scripts/sync.sh
```

这个脚本会做四件事：
1. `git pull` 拉取 main 最新内容（包含所有人的契约更新）
2. 打印"本次拉到的契约变更"—— 让你立刻知道谁改了什么
3. 重新加载 Hive 建表 SQL（如果有变动）
4. 检查你的本地环境和契约是否一致

**所以你的标准工作流是：**
```
开工 → bash scripts/sync.sh → 看到契约变更 → 按新契约干活
```
