## 二、文件清单（实测）

### 2.1 时序类（6 个文件）—— **宽表结构**

**共同结构**：`time` 列 + **275 个分区列**（列名即分区 ID，如 `102`、`104`、`1066`）

| 文件 | 大小 | 行数 | 指标含义 | 单位 |
|---|---|---|---|---|
| `occupancy.csv` | 19.1 MB | 4,344 | 充电桩占用率 | 比例 0~1 |
| `duration.csv` | 17.0 MB | 4,344 | 充电总时长 | 小时 |
| `volume.csv` | 15.7 MB | 4,344 | 充电总电量（按桩额定功率推算） | kWh |
| `volume-11kW.csv` | 18.8 MB | 4,344 | 充电总电量（按 11kW 标准车型口径） | kWh |
| `e_price.csv` | 11.5 MB | 4,344 | 电价 | 元/kWh |
| `s_price.csv` | 14.3 MB | 4,344 | 服务费 | 元/kWh |

**表头示例（前 6 个分区）**：
```
time,102,104,105,106,107,...
2022-09-01 00:00:00,0.5666666666666667,0.05263157894736842,...
```

> 🔴 **给苏静的建表提示**：
> 宽表有 276 列，Hive 建表时不要手写 275 个字段名。
> **推荐做法**：ODS 层用 `ROW FORMAT DELIMITED FIELDS TERMINATED BY ','` + `TBLPROPERTIES` 配合 **SerDe 自动建表**（下面第五节给了完整 DDL）。
> ODS 保留宽表原貌 → DWD 层用 `stack()` 或 `lateral view explode()` **炸成标准长表**（zone_id, hour_ts, metric, value）→ 后续 DWS/ADS 全部基于长表计算。
> 这正是"ETL"里 E（Explode）那一步，技术上非常扎实。

### 2.2 维表类（3 个文件）

#### `inf.csv` —— 分区基础信息（275 行 + 表头）

| 字段 | 类型 | 单位 | 含义 |
|---|---|---|---|
| TAZID | string | — | 交通分区编号（**注意是字符串**） |
| longitude | double | — | 经度（WGS84） |
| latitude | double | — | 纬度（WGS84） |
| **charge_count** | int | 个 | **该分区充电桩总数 ← 需求强度的分母** |
| area | double | m² | 分区面积 |
| perimeter | double | m | 分区周长 |

**实测**：275 个分区，充电桩总数 **23,441**（min=4，max=446）

> ❌ **本文件没有"是否分时电价"标识字段，也没有 capacity / in_cbd 字段。**
> 分时电价区的识别只能走 `e_price.csv` 的**时序标准差**路线（见第五节）。
> 容量可用 `charge_count` 近似代替。

#### `adj.csv` —— 分区邻接矩阵（275 × 275）
行名 = 分区 ID，列名 = 分区 ID，值 0/1 表示是否相邻。无表头行标签列，行标签即第一列。

#### `distance.csv` —— 分区距离矩阵（275 × 275）
结构同 `adj.csv`。实测值如 `1809.44`、`2196.93`，**单位未标注，推断为米**（相邻分区中心距离量级合理）。C 组需在报告里注明这是推断值。

## 四、关键 join 键与分区键

| 用途 | 键 | ⚠️ 注意 |
|---|---|---|
| **时序表内部** | 列名即 zone_id | Hive 里要把列名转成行值才能用 `group by zone_id` |
| **时序表 ↔ inf** | `zone_id = TAZID` | **TAZID 是 string，时序列名也是 string，转 int 后再 join** |
| **时序表 ↔ weather** | `hour_ts` | **两边时间格式不同，必须先统一** |
| **poi ↔ 分区** | 经纬度空间连接 | 不能按行号，用距离最近 |
| **adj / distance** | 行列索引即 zone_id | 矩阵无时间维度，是静态维表 |
| **Hive 分区键** | `dt`（yyyy-MM-dd），时序表用 | 275 分区宽表建议按 `dt` 分区 |
| **Hive 分桶键** | `zone_id` | 长表层用 |

## 五、给苏静的建表建议（可直接照抄）

### 5.1 ODS 层 —— 宽表原样落地

```sql
-- 通用建表模板：六个时序文件结构一致，只是路径不同
CREATE DATABASE IF NOT EXISTS uev_ods;

CREATE TABLE IF NOT EXISTS uev_ods.occupancy (
  `time` STRING,
  `102` DOUBLE, `104` DOUBLE, `105` DOUBLE
  -- ... 实际列名请用脚本从 CSV 表头自动生成，见下方生成脚本
)
COMMENT '充电桩占用率（宽表，来自 UrbanEV occupancy.csv）'
STORED AS ORC
TBLPROPERTIES ('orc.compress'='SNAPPY');
```

> 💡 **275 列手写不现实**，用这段 Python 脚本自动生成 DDL：
> ```python
> import csv, io
> with io.open('data/raw/occupancy.csv', encoding='utf-8') as f:
>     cols = next(csv.reader(f))[1:]
> ddl_cols = ",\n  ".join("`%s` DOUBLE" % c for c in cols)
> print("CREATE TABLE uev_ods.occupancy (\n  `time` STRING,\n  %s\n)\nSTORED AS ORC;" % ddl_cols)
> ```

### 5.2 DWD 层 —— explode 成长表（**ETL 的核心步骤**）

```sql
CREATE DATABASE IF NOT EXISTS uev_dwd;

CREATE TABLE IF NOT EXISTS uev_dwd.zone_hour_metric (
  zone_id   STRING  COMMENT '交通分区编号',
  hour_ts   STRING  COMMENT '小时时间戳 yyyy-MM-dd HH:mm:ss',
  dt        STRING  COMMENT '日期分区键 yyyy-MM-dd',
  hour_of_day INT   COMMENT '0-23',
  metric    STRING  COMMENT 'occupancy/duration/volume/volume_11kw/e_price/s_price',
  value     DOUBLE  COMMENT '指标值'
)
COMMENT '各指标标准化长表（由 ODS 宽表 explode 而来）'
PARTITIONED BY (dt STRING)
STORED AS ORC
TBLPROPERTIES ('orc.compress'='SNAPPY');
```

**explode 写法（Hive 3.x，列名动态展开）**：
```sql
INSERT OVERWRITE TABLE uev_dwd.zone_hour_metric PARTITION (dt)
SELECT zone_id, hour_ts, dt, hour_of_day, metric, value
FROM uev_ods.occupancy
LATERAL VIEW STACK(1, 'occupancy', `102`, '104', `105`, ...)  -- 275 列手写太长
       t AS metric, value
```
> 💡 **更实用的做法**：用 Hive 的 `stack` 需要硬编码列名，建议改用 **Spark SQL 的 `melt`** 或
> **写 MapReduce/Mapper 做 explode**（这正好是 B 岗 MR 清洗作业的用武之地）。
> **或者**：直接用 Spark 读 CSV 时 `option("header",true).option("inferSchema",true)` +
> `melt("zone_id","value", ...)` —— 但 melt 需要动态列名。
> **推荐**：B 岗用 **MapReduce 手写 Mapper 做列转行**，作为 MR 作业的经典案例，最能体现"Hadoop 熟练掌握"。

| # | 坑 | 现象 | 处理 |

## 七、创新点②的可行实现路径（给姬婷婷）

**没有现成的"是否分时电价"字段，但可以用价格波动反推**：

```sql
-- 分区 z 的电价时序标准差
SELECT zone_id, STDDEV_POP(value) AS price_std
FROM uev_dwd.zone_hour_metric
WHERE metric = 'e_price'
GROUP BY zone_id;

-- 判定
--   price_std > 阈值  → 该分区实行分时电价
--   price_std ≈ 0     → 该分区执行固定电价
```

**进一步**：算出每个分区的**峰谷电价差** `max(e_price) - min(e_price)`，
按这个差值把 275 个分区分成"分时电价组"和"固定电价组"，
再对比两组的**占用率曲线**（低谷时段占比、高峰时段占比），
就能量化"分时电价对削峰填谷的实际效果" —— 这就是创新点②的完整逻辑闭环。

> 💡 **这个点的价值**：全深圳 275 个分区的真实分时电价策略是公开信息，
> 但**"分时电价区 vs 固定价区的占用率曲线对比"这个分析角度是本项目独有的**。
